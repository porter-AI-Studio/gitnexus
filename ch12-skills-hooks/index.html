第 12 章 · Part 4：MCP 整合與 Agent 實戰

Agent Skills 與 Hooks 自動化工作流

讓索引隨程式碼自動更新，Skills 隨專案自動生成

AI 協作的關鍵思維：Skills 是建議書，Hooks 是合約

在引導 AI Agent（例如 Claude Code、Cursor 等）與中大型專案進行協作時，如何提供規範與限制是一個關鍵問題。 很多人傾向於往 System Prompt 或 `.clauderc` 規則文件裡寫入一長串「請每次都執行 X 命令」或「修改此檔案前必須先做 Y」。

然而，這類文字指引在大上下文場景下會面臨嚴重的選擇性遗忘。 為了解決這個瓶頸，我們必須區分兩大協作機制：

  • Skills（技能/建議）：使用 Markdown 文件撰寫，提供 AI 在特定主題（如代碼探索、重構）時的引導。它像是一本「操作建議書」，適合用於給予大方向和邏輯框架。
  • Hooks（鉤子/強制）：使用實體程式碼腳本撰寫（如 JS 腳本），直接攔截 AI Agent 的工具調用事件。它是「硬性合約」，一旦觸發事件（例如寫檔或 commit），100% 強制執行，繞過 LLM 的主觀判定。

這帶來了黃金協作原則：用 Skills 給方向，用 Hooks 定底線。

Agent Skills 的運作機制

當執行 gitnexus analyze --skills 時，GitNexus 會讀取第 9 章提到的 Leiden 社群偵測結果，為各個緊密的功能模組生成對應的 SKILL.md， 寫入到本地 .claude/skills/generated/ 下。

一個生成後的 SKILL 結構如下：

.claude/skills/generated/auth-skill.md 
# SKILL.md (由 gitnexus analyze --skills 自動生成)
# 模組: Authentication & Session Management

## 關鍵檔案 (Files)
- src/auth/login.ts   - 登入邏輯與密碼驗證
- src/auth/session.ts - 階段管理與驗證過期
- src/auth/jwt.ts     - JWT Token 簽署與校驗

## 核心入口點 (Entrypoints)
- loginHandler (src/auth/login.ts:L45)
- verifySessionMiddleware (src/auth/session.ts:L12)

## 執行流程 (Processes)
- process_login: loginHandler -> validatePassword -> signToken -> createSession
- process_verify: verifySessionMiddleware -> checkExpiration -> refreshSession

每當 AI Agent 開始操作 `src/auth` 目錄時，Astro/Claude 會自動載入這份指引，讓 AI 立刻對此模組的核心檔案、入口、甚至是預先算好的 Processes（執行流程）瞭如指掌， 不需要反覆 grep，省下近 95% 的探索用 Token。

內建 4 大核心 Skills

GitNexus 預載了 4 大主題 Skill 包，協助 AI 在專案中扮演不同角色：

Skill 作用描述 AI Agent 執行效果
Exploring 引導 AI 理解代碼結構、模組關係與資料流向 AI 不會再盲目 grep，而是先用 context/query 工具拉取結構圖。
Debugging 針對報錯、日誌或 CI 失敗，從入口點開始向下追溯呼叫鏈 AI 能以 runtime process 為線索，快速定位故障源頭的函數。
Impact Analysis 在修改任何關鍵型別或底層函式前，先做爆炸半徑分析 強制 AI 先呼叫 `gitnexus_impact`，評估改動風險等級，防範改 A 掛 B。
Refactoring 執行安全重命名、重複代碼提取與模組解耦 AI 會先用 `gitnexus_rename` 工具掃描所有影響點，再一次性安全重構。

Hooks：保持地圖最新（Stale Index 防禦）

使用圖譜最致命的陷阱是：地圖一旦過期，就會開始誤導。 如果開發者修改了代碼，而沒有及時重新索引，AI Agent 拿到的就是舊的呼叫圖，此時進行爆炸半徑分析反而容易漏掉新引入的呼叫。

為了防止這個隱患，GitNexus 配置了 PostToolUse Hook。 每次當 AI 執行提交代碼（git commit）或者是大幅度修改檔案後，Hook 會自動攔截並觸發重新索引：

.claude/hooks/postToolUse.js 
// .claude/hooks/postToolUse.js (或者 .clauderc.json 中的 hooks 設定)
// 每次 git commit 或者是寫檔後，自動觸發檢查
module.exports = async function postToolUse(event) {
  const { tool, result } = event;
  
  // 偵測是否執行了 git commit 或大量代碼修改
  if (tool === 'run_command' && result.command && result.command.includes('git commit')) {
    console.log('[GitNexus Hook] 檢測到代碼提交，正在更新知識圖譜索引...');
    
    // 執行增量索引更新
    const { exec } = require('child_process');
    exec('npx gitnexus analyze', (err, stdout, stderr) => {
      if (err) {
        console.error('[GitNexus Hook] 索引更新失敗:', stderr);
      } else {
        console.log('[GitNexus Hook] 知識圖譜增量索引更新完成！');
      }
    });
  }
};

透過將「重新索引」的職責寫在 Hook 裡，開發者和 AI Agent 無需手動記錄何時需要 analyze，系統會自行硬性把關，確保地圖永不過期。

PreToolUse Hook：圖譜上下文自動注入

另一個實用場景是 PreToolUse Hook。 當 AI 嘗試使用 `view_file` 或 `grep_search` 時，Hook 會在工具執行前自動以被查檔案為 node，呼叫 GitNexus 把該檔案關聯的 360 度結構（Imports、Defines、鄰居節點）以極精簡的 summary 格式塞進對話中。 這實現了「無感」的架構感知——AI 在查檔案內容的瞬間，背景已經自動拿到了關係圖譜的上下文。

本章小結

在 AI Coding 的大航海時代，我們不能僅指望自然語言的 Skills 來規範 AI 行為。 GitNexus 透過 Leiden 演算法自動生成專案專屬 Skills 解決「代碼架構理解」問題，提供局部大方向； 並透過 Pre/PostToolUse Hooks 建立程式級的攔截，確保圖譜在每次變更後自動完成增量更新。 兩者結合，才能在不耗費多餘 Token 的前提下，打造出一套真正穩定、精確、持續保鮮的 AI 自動化工作流。
