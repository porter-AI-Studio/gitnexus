第 9 章 · Part 3：核心架構原理

Leiden 社群偵測與執行流程追蹤

讓圖譜自動長出「功能模組」與「執行流」的兩個關鍵演算法

痛點：龐大無序的關係網與 LLM 的注意力極限

經過 AST 解析與跨檔案連結後，GitNexus 在 LadybugDB 中建立了一張由成千上萬個節點（Symbol）與邊（Calls、Imports）組成的超大型網狀結構。 此時若將整張圖的原始資料（包含所有細碎的方法與變數連結）直接拋給 AI Agent，將會面臨嚴重的工程問題：

  • Token 爆炸：即使是中型專案，包含關係的原始文本也會迅速塞滿 LLM 的 Context Window。
  • 注意力缺失：網狀關係的無序度（Noise）過高，LLM 很難在單次對話中梳理出高層次的架構邊界，容易在推理過程中產生答案漂移。

為了解決這個問題，GitNexus 引入了 Leiden 社群偵測（Community Detection） 與 執行流程追蹤（Processes Tracing），在索引階段（Index Time）就預先為 AI 整理好程式碼庫的高層次劃分。

Leiden 社群偵測演算法

Leiden 演算法是圖論中用於偵測「社群結構」的經典演算法（它是 Louvain 演算法的改進版）。 其核心思想是：在同一個功能模組內部，符號之間的呼叫關係通常非常緊密（高內聚）；而不同模組之間的呼叫則相對稀疏（低耦合）。

Leiden 演算法相較於舊款 Louvain 具有以下三個核心工程優勢：

  1. 消除不連通社群：Louvain 在運作時，可能會將在物理上完全不相連的符號硬塞進同一個社群中。Leiden 在運算過程中會動態消除這些低品質的社群。
  2. 極佳的確定性：相同代碼結構在多次執行索引時，Leiden 能保證生成幾乎完全一致的社群分群。這對 incremental index（增量索引）至關重要，可避免每次 commit 後圖譜結構發生劇烈抖動。
  3. 高運算效能：時間複雜度約為 $O(N \log N)$（其中 $N$ 為節點數），對於擁有數十萬行代碼的大型 Monorepo 也能在數秒內完成分組。

Leiden 偵測結果與 `registry.json` 結構

Leiden 偵測完成後，會將每個符號打上對應的 `clusterId` 標籤，並將社群的 Metadata 寫入本地的 `.gitnexus/registry.json` 中。 下面是一個實際生成的結構範例：

Leiden Cluster 資料結構 
// Leiden 演算法生成的功能集群配置（寫入 .gitnexus/registry.json）
{
  "clusters": [
    {
      "id": "cluster_auth",
      "name": "authentication",
      "cohesion": 0.89,
      "entrypoints": [
        "src/auth/login.ts::validateSession", 
        "src/auth/jwt.ts::signToken"
      ],
      "files": [
        "src/auth/login.ts",
        "src/auth/jwt.ts",
        "src/auth/session.ts"
      ]
    },
    {
      "id": "cluster_payment",
      "name": "payment_gateway",
      "cohesion": 0.92,
      "entrypoints": [
        "src/payment/checkout.ts::processOrder"
      ],
      "files": [
        "src/payment/checkout.ts",
        "src/payment/stripe.ts",
        "src/payment/paypal.ts"
      ]
    }
  ]
}

執行流程追蹤（Processes Tracing）

單純的社群偵測（Leiden）告訴我們「代碼庫有哪些功能板塊」，但開發者在修改代碼時，最關心的是「業務執行鏈路」。 例如：「當用戶發起 API 請求後，代碼是怎麼流轉到資料庫的？」

執行流程追蹤（Processes Tracing） 透過識別「已知入口點（Entrypoints）」，向下遍歷 Calls 關係網，建立一條條清晰的有向子圖。

1. 識別 Entrypoints（入口點）

GitNexus 的 [routes] 和 [tools] 子解析器會自動標記以下符號為 `isEntrypoint: true`：

  • HTTP Route Handlers（例如 FastAPI 路由、Express 路由、Next.js API routes）。
  • 程式進入點（例如 Go/Rust/Java 的 `main` 函數）。
  • 異步任務監聽器（例如 Message Queue Consumer、Cron Job 執行器）。

2. 深度遍歷與路徑生成

從 Entrypoint 出發，沿著圖的 Calls 邊向下探測。為了避免陷入循環呼叫（如遞迴）並維持 Context 的精簡，GitNexus 會限制追蹤的最大深度（預設為 5 跳）。

執行流程 Cypher 追蹤邏輯 
// processes 階段追蹤的執行流程子圖 (LadybugDB OpenCypher 表示)
// 查找由 Entrypoint 出發的所有可達路徑
MATCH path = (e:Symbol {isEntrypoint: true})-[:Calls*1..5]->(downstream)
RETURN path
LIMIT 100;

// 回傳的執行流程結構：
// process_checkout: checkout() -> validatePayment() -> formatCurrency() -> db.save()

社群偵測與流程追蹤對 AI Agent 的真實價值

1. 自動生成專屬 Skills（--skills 參數）

當你在執行索引時加上 gitnexus analyze --skills，GitNexus 會將 Leiden 算法識別出的每個功能社區轉換成獨立的 SKILL.md， 寫入專案根目錄的 .claude/skills/generated/<area>/ 底下。

這意味著：當 AI Agent 進入 `payment/` 模組修改代碼時，它會自動加載 payment 的專屬 Skill，只關注 payment 社群內的文件、入口點與邊界， 而不會被 `auth/` 或 `user/` 的無關文件干擾，Token 消耗量大幅降低 50% 以上。

2. 精確的變更影響分析（detect_changes）

當你修改了程式碼並執行 git diff 時，detect_changes 工具可以利用 `Processes` 圖譜直接告訴你： 「你的這項修改，影響了 `process_checkout`（訂單結帳流程）與 `process_refund`（退款流程）。」 這比傳統的「哪些檔案被修改」更貼近真實的業務視角。

💡
什麼是置信度評分（Confidence Score）？

在動態語言（如 Python、JavaScript）中，由於存在動態分派（Dynamic Dispatch）與鴨子型別（Duck Typing），靜態分析無法 100% 確定某些呼叫關係。 GitNexus 會在邊上標記置信度（Confidence: 0.0 ~ 1.0）。 Leiden 演算法在聚類時會根據這個分數進行加權，置信度過低的邊會被自動排除，確保生成的功能集群不受錯誤推論的干擾。

本章小結

Leiden 社群偵測演算法利用代碼呼叫關係的拓撲凝聚力，將無序的代碼網自動劃分為內聚的功能集群（Clusters），並透過 `--skills` 自動生成專案的模組指引； 執行流程追蹤則從 Entrypoint 開始向下遍歷，建立動態業務流向圖。 兩者配合，將複雜的 Codebase 結構在索引時完成「因式分解」，讓 AI Agent 可以隨時以最精簡、最精確的局部架構上下文工作。
