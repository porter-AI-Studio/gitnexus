第 2 章 · Part 1：認識 GitNexus

AI Coding 的結構盲點：為什麼需要知識圖譜

AI 盲改程式碼的根源，不是模型不夠聰明，而是看不見結構

一個典型的「盲改」現場

你大概也遇過這種情況——

接手一個新專案，git clone 完打開 IDE，幾百個資料夾、上千個檔案鋪天蓋地。你想改個登入邏輯，結果改了 A 檔案，B 檔案掛了；改了 B 檔案，C 介面又報錯。於是你把問題丟給 AI 編程助手：「這段程式碼的呼叫鏈是什麼？」它開始瘋狂地 grep、glob、讀檔案——Token 燒掉好幾萬，給你的答案還是斷章取義。

更危險的版本是：AI 直接動手改了。它修改了一個函數的回傳型別，卻不知道有 47 個其他函數依賴這個回傳型別——破壞性變更就這樣被輕易提交。等到 CI 紅燈、或更糟——上了 production 才爆炸，你才發現 AI 從頭到尾沒「看見」那些依賴。

Claude Code、Codex、Cursor 在局部任務裡都表現得像高手，但一進大型 codebase，常見失誤出奇地一致：

  • 改了一個回傳型別，不知道下游有多少依賴
  • 看到一個 API handler，卻不知道真正的 consumer 在哪裡
  • 只憑關鍵字搜尋，忽略 hidden dependency
  • rename 某個 symbol，漏掉跨檔與跨流程的關聯

根本原因：不是模型不夠聰明，而是看不見結構

很多人把這個問題歸咎於「模型還不夠強」。但只要觀察 AI 檢索過程的中間步驟就會發現：大部分時間它都在做關鍵字過濾——grep 搜尋、檔案讀取、語義比對。這些方法能找到「程式碼在哪裡」，但找不到「程式碼之間的關係」。

關鍵在於一個維度落差：

程式碼是線性的文本，但架構是網狀的。讓 AI 用「讀檔案」的方式理解一個網狀結構，就像用一維的尺去量三維的立體——永遠差一個維度。

依賴關係、呼叫鏈路、執行流程——這些結構性資訊，在普通的檔案搜尋裡是丟失的。AI agent 看到的永遠是檔案片段，不是程式碼結構。它不是不會寫 code，而是缺一張夠完整的地圖。

ℹ️
瓶頸正在從「程式碼生成」轉向「程式碼理解」

生成一段程式碼很容易，但理解這段程式碼在整個系統中的位置、修改它會產生什麼連鎖反應，才是真正困難的部分。GitNexus 想補的，不是另一個更會聊天的介面，而是 AI Coding Agent 在大型 codebase 裡最缺的那張結構地圖。

AI 在大型 Repo 的三大痛點

痛點 具體表現 後果
1. 依賴追蹤失敗 只能看到直接 import，看不到透過中間層的間接依賴與傳遞依賴；hidden dependency 完全隱形 「改 A 掛 B」事故，破壞性變更被輕易提交
2. 呼叫鏈不可見 一個函數的上游呼叫者、下游被呼叫者、橫向共享資料結構的模組，需要 Ctrl+點擊跳轉 N 次才能拼湊出來 AI 只能交出「看起來合理的局部答案」，指不出真正的上下游路徑
3. 重複 grep 浪費 Token 理解一個模組要 grep 十幾輪、讀十幾個檔案，每輪結果再塞回 context window Token 成本暴增、context window 被檔案內容塞爆、長上下文中答案漂移

以一個實際例子來說：假設你要修改 AccountService 裡的 read 方法，用普通搜尋你能找到方法定義和一些呼叫點，但你很難一次看清楚：

  • 哪些 Controller 直接呼叫了這個方法？（直接依賴）
  • 這些 Controller 又被哪些路由引用？（間接依賴）
  • 修改這個方法會影響到哪些執行流程？（爆炸半徑（Blast Radius））
  • 有沒有其他 Service 透過中間層間接依賴它？（傳遞依賴）

這些關係在 codebase 裡是隱含的——需要一個人花很長時間追蹤才能理清，而 AI agent 在每一次對話裡都得從零重新追一遍。

傳統做法為何不夠

在知識圖譜出現之前，AI 編程工具理解程式碼的手段大致有三種：grep 關鍵字搜尋、全文／語義搜尋、通用 RAG。它們都有同一個致命傷——回傳的是程式碼片段，不是程式碼關係。

方法 能做到 做不到 對 AI 的代價
grep / Glob 找到符號出現的位置 分不清定義、呼叫、同名字串；看不到間接依賴 逐檔案掃描，十幾輪工具呼叫起跳
全文／語義搜尋 用自然語言找到「相關」的程式碼片段 「相關」不等於「有依賴關係」；呼叫鏈依然不可見 回傳片段仍需 AI 自行讀檔拼湊
通用 RAG 把原始程式碼片段塞給 LLM 關係要 LLM 自己「發現」，多跳推理容易漏 需要多次查詢鏈，長上下文漂移
知識圖譜（GitNexus） 一次查詢拿到完整呼叫鏈、依賴與影響範圍 — 單次工具呼叫，0 次盲目讀檔

GitNexus 官方對此有一個很精準的對比：傳統 RAG 是把原始程式碼片段扔給 AI，讓它自己去發現關係；GitNexus 是把預先計算好的關係直接給 AI，一次呼叫就能拿到完整上下文。這就是「預計算關係智慧」（precomputed relationship intelligence）——把理解結構的重活從推理時間（inference time）移到索引時間（index time）。

知識圖譜如何補上全局視角

GitNexus 的做法是：在索引階段就用 Tree-sitter 解析所有原始碼，提取函數、類別、方法之間的真實呼叫關係，把節點與關係存進本地圖資料庫 LadybugDB，並預先算好 dependency、call chain、功能集群（cluster）、執行流程（process flow）與影響範圍。AI 不再是瞎子摸象，而是帶著地圖行走。

最能體現差異的場景，就是「修改前先看爆炸半徑」。下面是同一個任務在兩種模式下的對照：

沒有圖譜：grep 式盲改 
你> 我要修改 auth/login.ts 裡 validateSession 的回傳型別，幫我改

Agent> 好的，讓我先了解一下這個函數...
  [Grep] "validateSession"          → 找到 23 個檔案
  [Read] auth/login.ts              → 讀取 480 行
  [Read] auth/session.ts            → 讀取 312 行
  [Grep] "session.validate"         → 又找到 11 個檔案
  [Read] api/middleware.ts          → 讀取 650 行
  [Read] api/routes/user.ts         → 讀取 220 行
  ...（持續 grep 與讀檔，共 14 輪工具呼叫）

Agent> 我已修改 validateSession 的回傳型別，
       並更新了 3 個我「找到的」呼叫點。

# 兩小時後：CI 紅燈
# payment/checkout.ts 透過中間層間接依賴 validateSession
# —— 它從頭到尾沒出現在任何一次 grep 結果裡
有圖譜：修改前先看 Blast Radius 
你> 我要修改 auth/login.ts 裡 validateSession 的回傳型別，幫我改

Agent> 修改前先做爆炸半徑（Blast Radius）分析...
  [MCP] gitnexus_impact target="validateSession" direction="upstream"

  ── Impact Report ──────────────────────────────
  d=1 直接依賴（必須同步修改）：4 個呼叫者
      loginHandler, refreshToken, ssoCallback, apiGuard
  d=2 間接依賴（需要測試確認）：9 個符號
      含 payment/checkout.ts 的 requireSession ← 注意！
  d=3 傳遞依賴：3 條執行流程經過此函數
  風險等級：HIGH（位於 auth 核心路徑）
  ───────────────────────────────────────────────

Agent> 這次修改的風險等級是 HIGH，
       影響範圍包含 payment 流程的間接依賴。
       我會一次更新全部 4 個直接呼叫點，
       並提醒你 checkout 流程需要回歸測試。

# 一次 MCP 查詢，0 次盲目讀檔，沒有漏網之魚

有了圖譜之後，impact 分析可以分層回報依賴深度——d=1 直接依賴必須同步修改、d=2 間接依賴需要測試確認、d=3 傳遞依賴若在關鍵路徑上也要驗證——並給出 LOW / MEDIUM / HIGH / CRITICAL 的風險等級。AI agent 收到 HIGH 或 CRITICAL 警告時會主動提醒你，而不是悶頭改完才讓 CI 來宣判。

這帶來三個直接的品質提升：

  • 可靠性：LLM 不會遺漏上下文，因為完整關係已經包含在工具回應裡
  • Token 效率：不需要 10 次查詢鏈才能理解一個函數
  • 事故率下降：改之前先看一眼影響半徑，大幅減少「改 A 掛 B」事故
💡
對照實驗：最快看出差異的方法

拿同一個問題——例如「改這個函數的回傳型別會影響哪些模組？」——分別用「純 Claude Code 搜尋」和「加上 GitNexus」各跑一次。不用圖譜時，agent 常常只能交出看起來合理的局部答案；加上圖譜後，它能直接指出真正的上下游路徑和風險半徑。這一題做得穩不穩，就是工具對 AI coding workflow 有沒有真實價值的分水嶺。

本地索引：成本、穩定性與小模型相容性

GitNexus 還有一個第一眼容易被低估的設計：核心索引流程幾乎完全在本地完成，不依賴雲端 LLM。repo 索引、呼叫鏈與依賴解析、cluster／process 建立、impact 與 query 等核心能力，全部不需要先接一把雲端 API key 就能運作。這正是「零伺服器（Zero-Server）」架構的體現——所有資料留在本地 .gitnexus/ 目錄，不上傳任何外部伺服器。

優勢 說明
成本 結構解析不消耗任何 LLM Token；不必每次理解 repo 都讓雲端模型從頭重讀一遍
穩定性 確定性的本地解析結果，不會像長上下文、多輪搜尋那樣產生答案漂移；同一個查詢永遠回傳同一張圖
小模型相容性 「模型民主化」——繁重的結構理解工作由工具承擔，較小的 LLM 也能拿到接近大模型上下文的結構視野
隱私合規 CLI 模式零網路請求，程式碼不離開本機，對有嚴格資料合規要求的企業是關鍵優勢

當然，GitNexus 並非完全不碰 LLM——像 gitnexus wiki 這類自動生成說明文件的功能就會走 LLM 路線。但這個切分很合理：理解結構靠本地索引，生成解釋才交給模型。

零 Token 消耗的意義

「零 Token 消耗」指的不只是省錢，而是改變了 AI 理解程式碼的經濟模型。

沒有圖譜時，AI 對 repo 的每一分理解都是「租來的」——每次對話都要重新 grep、重新讀檔、重新燒 Token，session 一結束，理解歸零。有了本地圖譜之後，結構理解變成「買斷的」——索引一次（中等規模專案不到 30 秒），之後每一次查詢都是本地圖資料庫的毫秒級操作，Token 帳單上是零。

這還連帶解決了 context window 的問題：傳統方式下，AI 需要讀 10 個檔案才能理解一個模組，幾千行原始碼把 context window 塞爆，真正的任務指令反而被稀釋；圖譜方式下，AI 一條查詢拿到濃縮後的結構化上下文，0 次檔案讀取，context window 留給真正重要的東西。

⚠️
圖譜不是一勞永逸：過期的地圖比沒有地圖更危險

所有圖譜型工具都有同一個現實：圖一旦不是最新，就會開始誤導。程式碼提交後記得重新執行 gitnexus analyze 做增量更新，並養成用 gitnexus status 檢查索引是否 stale 的習慣。Claude Code 使用者有 PostToolUse hook 在 git commit 後自動提醒重新索引——索引保鮮的細節會在後續章節詳細說明。

本章小結

AI 編程助手在大型 repo 裡的「盲改」，根源不是模型能力不足，而是它看到的永遠是線性的檔案片段，而非網狀的程式碼結構。grep、全文搜尋、通用 RAG 都只能回傳「片段」，無法回傳「關係」——依賴追蹤失敗、呼叫鏈不可見、重複搜尋浪費 Token，三大痛點由此而生。

知識圖譜的解法是把關係預先計算好：索引時用 Tree-sitter 解析結構、存入 LadybugDB、透過 MCP 讓 agent 一次查詢拿到完整上下文。修改前先看爆炸半徑（Blast Radius），改完前先跑變更檢測；本地索引讓這一切零 Token 消耗、結果穩定、連小模型也能受惠。

下一章我們會把「知識圖譜」這個詞拆開來，與 Vector RAG、Graph RAG 做正面對比——看清楚 GitNexus 的「預計算關係智慧」與傳統檢索增強方法在原理上的根本差異。
