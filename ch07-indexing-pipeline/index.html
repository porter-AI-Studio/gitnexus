第 7 章 · Part 3：核心架構原理

索引管線深度解析

12 個階段，從原始碼到知識圖譜的完整旅程

全局流程圖

一行 gitnexus analyze 背後，是 12 個階段的管線串聯執行：

完整的 12 階段結構

12 階段索引管線 
# 12 階段索引管線（完整序列）
scan
  └─ structure
       ├─ [markdown]          # Markdown 文件解析（文件節點）
       ├─ [cobol]             # COBOL 特殊語法處理
       └─ parse
              ├─ [routes]     # 路由偵測（Express/FastAPI/Next.js 等）
              ├─ [tools]      # 工具/函式工具定義偵測
              ├─ [orm]        # ORM 模型關係偵測（Prisma/SQLAlchemy 等）
              └─ crossFile
                      └─ mro
                           └─ communities
                                   └─ processes

各階段詳解

Stage 1：scan — 建立檔案清單

遍歷整個 repo 目錄樹，建立要索引的檔案清單。根據語言副檔名分類（.ts、.py、.java 等），跳過 .gitignore、node_modules、二進制檔案、超大型檔案。同時讀取 .gitnexus/registry.json 的上次索引記錄，確定哪些檔案是新增或修改過的（增量索引的基礎）。

Stage 2：structure — 模組與包結構

建立高層模組結構：識別 package.json、pyproject.toml、go.mod 等專案描述檔，解析命名空間、包層次、模組邊界。這個階段建立的是「容器節點」（模組、包），後續的符號解析會把函式、類別等掛在對應容器下。

特殊語言在 structure 後插入：Markdown（建立文件節點，關聯到程式碼符號）、COBOL（特殊行格式前置處理）。

Stage 3：parse — Tree-sitter AST 解析（核心）

這是最重要的階段，所有程式碼符號都在這裡被提取。GitNexus 使用 Tree-sitter 對每個檔案建立精確的 AST（抽象語法樹），從中提取：

Tree-sitter 解析輸出的三類核心資訊 
// Tree-sitter 解析的三類核心資訊

// 1. Symbols（符號）— 節點
{
  type: "function" | "class" | "method" | "variable" | "interface" | "module",
  name: "validatePayment",
  file: "src/payments/validator.ts",
  startLine: 42,
  endLine: 67,
  signature: "(amount: number, currency: string) => Promise<ValidationResult>"
}

// 2. Edges（關係）— 邊
{
  type: "calls" | "imports" | "extends" | "implements" | "references",
  from: "checkout → validatePayment",
  to: "validatePayment → formatCurrency"
}

// 3. Clusters（集群）— Leiden 社群偵測
{
  id: "cluster_auth",
  members: ["login", "validateToken", "refreshSession", "logout"],
  cohesion: 0.87  // 集群內聚度評分
}

parse 後插入三個專業解析器：

  • [routes]：偵測 Express、FastAPI、Next.js App Router 等框架的路由定義，建立 HTTP route → handler function 的映射關係
  • [tools]：偵測 LLM Tool / Function Definition 格式（OpenAI tools、Claude tool_use、Anthropic SDK），讓 AI agent 知道哪些函式是工具
  • [orm]：偵測 Prisma schema、SQLAlchemy models、TypeORM entities，建立 ORM 模型 → 資料庫表格的關係節點

Stage 4：crossFile — 跨檔案依賴解析

crossFile 階段：解析跨檔案依賴與 mro 
# crossFile 階段：解析跨檔案依賴

# 輸入：各檔案內的未解析符號引用
# 輸出：填充圖譜中的 imports / references 邊

# 示例：payment.ts 引用了 validator.ts 的 validatePayment
import { validatePayment } from './validator';
# crossFile 階段：
# 1. 解析 './validator' 相對路徑 → 絕對路徑 src/payments/validator.ts
# 2. 在圖中建立邊：payment.ts → validatePayment（imports）
# 3. 解析 alias（tsconfig paths / webpack aliases）

# mro（Method Resolution Order）階段
# 解決繼承鏈：找到 BasePayment.process() → StripePayment.process() → 實際呼叫目標
# Python: C3 linearization MRO
# TypeScript: interface merging + class hierarchy
# Java: 依照 JLS 繼承規則

crossFile 解析 import/require/use 等語句，將同一 repo 內的相對路徑引用解析成絕對路徑，建立檔案間的 imports 邊。同時處理：tsconfig paths alias、webpack module alias、Python PYTHONPATH。

Stage 5：mro — 繼承鏈與多型解析

Method Resolution Order 階段解決繼承帶來的呼叫模糊性：

  • Python：依照 C3 MRO 算法（PEP 3141）建立類別繼承鏈
  • TypeScript：解析 interface 合併、class extends、implements 鏈
  • C#：解析 virtual/override 方法分派，interface 多型
  • Java：依照 JLS 規範處理方法覆寫

完成後，context 工具才能正確回答「這個 abstract method 的實際執行者是哪個子類」。

Stage 6：communities — Leiden 社群偵測

用 Leiden 演算法（Louvain 的改進版）對完整呼叫圖做社群偵測，自動把功能相關的符號歸入同一 Cluster。Leiden 的關鍵特性：

  • 保證找到分離的社群（Louvain 可能產生連通不好的社群）
  • 結果確定性高（相同圖輸入多次執行結果一致）
  • 複雜度 O(n log n)，適合大型 codebase

產出：每個 Cluster 有名稱（自動推斷或從主要函式名導出）、成員列表、內聚度評分。

Stage 7：processes — 執行流程追蹤

從已知入口點（API route handlers、main()、event handlers、scheduled jobs）向下追蹤完整呼叫鏈，建立「執行流程」——一條從入口到所有可達節點的有向子圖。

完成後，detect_changes 工具可以把「改了第 N 行」映射到「影響哪些執行流程」，而不只是「哪些函式直接呼叫」。

兩套呼叫解析路徑

Legacy DAG vs Scope-Resolution Pipeline 
# 兩套呼叫解析路徑

# Legacy Call-Resolution DAG（未遷移語言）
# 6 階段類型化管道（Go、Rust、PHP、Ruby、Java、Swift、C/C++、Dart 等）
# 流程：符號提取 → 作用域分析 → 型別推論 → 呼叫解析 → DAG 建立 → 邊寫入

# Scope-Resolution Pipeline（RFC #909 Ring 3，已遷移語言）
# Python、C#、TypeScript 採用新架構
# 流程：Registry 驅動，注册中心優先解析，支援動態分派與型別縮窄
# 優勢：精準解析 Python 的 duck typing、C# 的介面多型、TypeScript 的 union types
路徑 適用語言 特點
Legacy Call-Resolution DAG Go、Rust、PHP、Ruby、Java、Swift、C/C++、Dart 等 6 階段類型化管道，穩定成熟
Scope-Resolution Pipeline（RFC #909） Python、C#、TypeScript Registry 驅動，支援動態分派、型別縮窄、union types
ℹ️
為什麼要兩套解析路徑？

Python 的 duck typing、TypeScript 的 union/intersection types、C# 的 interface 多型，在靜態呼叫解析上比 Go 或 Java 困難得多——不能只靠靜態型別推論。RFC #909 Scope-Resolution Pipeline 引入了 Registry 驅動的解析，能在不執行程式碼的前提下，更精準地解析這三種語言的動態行為。

增量索引的實現原理

GitNexus 用檔案 hash + git 變更集的雙重策略決定哪些檔案需要重新解析：

  • 首次索引：對所有檔案走完 12 個階段
  • 後續索引：只對 hash 變更的檔案重新解析，然後更新圖中的相關邊
  • crossFile、mro 階段的結果會基於變更的符號集做局部更新，不需要全量重算
  • communities（Leiden）和 processes 階段目前仍是全量重算（因為全局圖結構可能改變）
💡
大型 Repo 的索引時間

根據社群報告，典型中大型 repo（10萬行以上）首次索引約 1-3 分鐘（不含 --embeddings）。加上 --embeddings 會增加語義向量計算時間，視 CPU 性能大約再多 2-5 分鐘。後續增量更新因為只重新解析變更檔案，通常在 10 秒內完成。

小結：為什麼預計算勝過 Runtime RAG

12 階段管線的最終產物是一個完整、精確、有向的知識圖譜，已經把以下所有工作做完：

  • 符號提取（所有函式、類別、方法）
  • 跨檔案依賴（完整 import 圖）
  • 繼承鏈解析（正確的多型目標）
  • 功能集群（Leiden 社群）
  • 執行流程（從入口點的完整呼叫鏈）

當 AI agent 呼叫 impact("validatePayment") 時，GitNexus 只需在圖上做一次 BFS 遍歷，毫秒級返回結果——不需要 LLM 去 grep、推論、再 grep。這就是「預計算優於 runtime 探索」的本質。
