多倉庫架構與 Docker 部署

從單一專案到微服務群：企業級的 GitNexus 用法

多倉庫架構概覽

GitNexus 天生支援多倉庫。每個 gitnexus analyze 的結果存在各自 repo 的 .gitnexus/ 目錄，同時登記到全局的 ~/.gitnexus/registry.json。 MCP 伺服器啟動後讀取這個清單，一個 gitnexus mcp 程序即可服務所有已索引的 repo， AI 工具呼叫時加上 repo 參數就能切換目標。

全局 Registry

Registry 是一份 JSON 清單，記錄每個 repo 的名稱、路徑、索引統計與最後 commit：

~/.gitnexus/registry.json 
// ~/.gitnexus/registry.json — 全局倉庫清單
[
  {
    "name": "backend",
    "path": "/Users/porter/projects/backend",
    "storagePath": "/Users/porter/projects/backend/.gitnexus",
    "indexedAt": "2026-06-10T10:30:00.000Z",
    "lastCommit": "a1b2c3d",
    "stats": {
      "files": 342,
      "nodes": 1248,
      "edges": 3891,
      "processes": 87,
      "embeddings": 1248
    }
  },
  {
    "name": "frontend",
    "path": "/Users/porter/projects/frontend",
    "storagePath": "/Users/porter/projects/frontend/.gitnexus",
    "indexedAt": "2026-06-10T09:15:00.000Z",
    "lastCommit": "f4e5d6c",
    "stats": {
      "files": 218,
      "nodes": 876,
      "edges": 2104,
      "processes": 52,
      "embeddings": 876
    }
  }
]

每個 Repo 的本地儲存

per-repo .gitnexus/ 目錄結構 
# 每個 repo 的本地索引結構
<repo>/.gitnexus/
  ├── lbug          # LadybugDB 資料庫本體（圖資料）
  ├── lbug.wal      # Write-Ahead Log（防止資料損毀）
  ├── lbug.lock     # 寫入鎖（確保單一寫入者）
  └── meta.json     # 上次索引時間、commit hash、統計數字

索引資料只存在本地——lbug 是 LadybugDB 資料庫本體， lbug.wal 是 Write-Ahead Log（保護資料完整性）， lbug.lock 確保同一時間只有一個寫入者。

多倉庫 MCP 操作

多倉庫索引與 MCP 啟動 
# 多倉庫管理基本指令

# 1. 分別索引每個 repo（各自注冊到全局 registry）
cd ~/projects/backend  &&  gitnexus analyze
cd ~/projects/frontend &&  gitnexus analyze
cd ~/projects/shared   &&  gitnexus analyze

# 2. 查看所有已索引的 repo
gitnexus list
# ● backend   (342 files, 1248 symbols) — current
# ● frontend  (218 files,  876 symbols) — stale (3 files changed)
# ● shared    ( 87 files,  412 symbols) — current

# 3. 啟動 MCP 伺服器（自動服務所有已索引的 repo）
gitnexus mcp

# 4. MCP 工具呼叫時加上 repo 參數鎖定目標
# "use gitnexus query on backend repo: authentication logic"
# "use gitnexus impact on frontend: UserCard"

repo 參數的三種解析方式

所有 MCP 工具都接受可選的 repo 參數，支援三種寫法：

MCP 工具的 repo 參數 
# MCP 工具的 repo 參數：三種解析方式

# 方式 1：用 registry 名稱（最簡潔）
query({ query: "authentication", repo: "backend" })
context({ name: "validateUser",  repo: "frontend" })
impact({ target: "AuthService",  direction: "upstream", repo: "shared" })

# 方式 2：用絕對路徑（同名衝突時必用）
query({ query: "auth", repo: "/Users/porter/work/backend" })
query({ query: "auth", repo: "/Users/porter/personal/backend" })

# 方式 3：查看所有已索引 repo 清單
# MCP 工具："use gitnexus list_repos"
# 或讀取 MCP 資源：gitnexus://repos
💡
同名衝突時用絕對路徑

如果你在工作目錄和個人目錄都有名為 backend 的 repo， repo: "backend" 會優先匹配名稱；衝突時，改用 repo: "/Users/porter/work/backend" 指定完整路徑。

Group 系統：跨 Repo 契約分析

多個獨立 repo 查詢只是「切換目標」，並非真正的跨服務分析。 GitNexus 的 Group 系統更進一步：把多個相互依賴的 repo 組成群組， 自動偵測 HTTP routes、gRPC endpoints、Kafka topics、shared libs 的跨服務契約， 讓 AI 可以追蹤跨越服務邊界的呼叫鏈。

group.yaml 格式

group.yaml — 多倉庫群組配置 
# ~/.gitnexus/groups/my-platform/group.yaml
version: 1
name: my-platform
description: "電商平台微服務群"

repos:
  auth/backend:   auth-service      # groupPath: registryName（階層路徑: registry 名稱）
  orders/api:     orders-service
  payments/api:   payments-service
  frontend/web:   web-app

links:                              # 手動宣告的契約（逃生艙：自動偵測偵測不到時用）
  - from: orders/api
    to:   auth/backend
    type: grpc                      # http | grpc | thrift | topic | lib | custom
    contract: "auth.AuthService/Login"
    role: provider                  # provider | consumer

detect:
  http: true
  grpc: true
  thrift: true
  topics: true                      # Kafka / NATS topic 追蹤
  shared_libs: true
  embedding_fallback: true          # 找不到靜態契約時用語義向量推測
  includes: false                   # opt-in：C/C++ #include 追蹤
  workspace_deps: false             # opt-in：Go/Elixir workspace 依賴

matching:
  bm25_threshold:       0.7
  embedding_threshold:  0.65
  max_candidates_per_step: 3
  exclude_links_paths:  ["/health", "/ready"]

群組管理指令

群組完整操作流程 
# 群組管理指令（完整流程）

# 1. 建立群組
gitnexus group create my-platform

# 2. 加入 repo（groupPath: 階層路徑, registryName: registry 中的名稱）
gitnexus group add my-platform auth/backend   auth-service
gitnexus group add my-platform orders/api     orders-service
gitnexus group add my-platform payments/api   payments-service
gitnexus group add my-platform frontend/web   web-app

# 3. 同步群組（提取契約 + 跨 repo 比對）
gitnexus group sync my-platform
# → 分析每個 repo 暴露的 HTTP routes、gRPC endpoints、函式介面
# → 跨 repo 比對：找出 A 呼叫而 B 定義的跨服務連結
# → 寫入 ~/.gitnexus/groups/my-platform/contracts.json

# 4. 查看契約
gitnexus group contracts my-platform
# grpc::auth.AuthService/Login    orders/api → auth/backend
# http::POST::/payments/charge    orders/api → payments/api
# topic::order.created            orders/api → frontend/web

# 5. 查看群組狀態（哪些 repo 需要重新索引）
gitnexus group status my-platform

# 6. 移除某個 repo
gitnexus group remove my-platform orders/api

跨 Repo 查詢語法

群組建立後，在 MCP 工具的 repo 參數前加 @ 即可把查詢廣播到整個群組，GitNexus 用 Reciprocal Rank Fusion（RRF）合併各 repo 的結果：

群組跨 repo 查詢 
# 跨 repo 群組查詢

# 在整個群組內搜尋（RRF 融合排名）
query({ query: "authentication flow", repo: "@my-platform" })

# 鎖定群組內某個成員
impact({ target: "AuthService", direction: "upstream", repo: "@my-platform/auth/backend" })

# 跨服務查詢時加上 service 範圍（monorepo 特別有用）
query({ query: "auth", repo: "@my-platform", service: "auth/backend" })

# 群組 MCP 資源
# gitnexus://group/my-platform/contracts   ← 合約清單
# gitnexus://group/my-platform/status      ← 每個 repo 的 stale 狀態
契約類型 自動偵測範例 group.yaml detect 選項
HTTP REST http::POST::/payments/charge http: true
gRPC grpc::auth.AuthService/Login grpc: true
Kafka Topic topic::order.created topics: true
共用函式庫 lib::@mycompany/utils shared_libs: true
語義推測 靜態分析無法確定時 embedding_fallback: true

生產環境用固定版本標籤

生產部署請避免 :latest，改用 :1.6.2 這類固定版本號， 確保不因非預期升級改變行為。每次升版前在暫存環境驗證索引相容性。

All-in-One 映像（第三方）

若想最簡單地用 Docker 啟動一個全功能 GitNexus（MCP + Web UI + HTTP API）， 社群維護的 mekayelanik/gitnexus-mcp 映像透過 HAProxy 把三個服務整合到單一埠口：

all-in-one docker-compose（第三方映像） 
# 第三方 all-in-one 映像（mekayelanik/gitnexus-mcp）
# 單一容器 + HAProxy：MCP + Web UI + HTTP API 全整合

services:
  gitnexus-mcp:
    image: mekayelanik/gitnexus-mcp:latest
    container_name: gitnexus-mcp
    restart: unless-stopped
    ports:
      - "8010:8010"          # 統一入口（HAProxy 代理）
    volumes:
      - /path/to/repos:/data:rw             # 原始碼（可讀寫，供自動重新索引）
      - gitnexus-registry:/home/node/.gitnexus
      - gitnexus-cache:/home/node/.cache
    environment:
      - PORT=8010
      - DATA_DIR=/data
      - NODE_ENV=production
      - API_KEY=your_bearer_token           # 可選：API 鑰匙保護
      - ANALYZE_EMBEDDINGS=false            # false 加快索引速度
      - WIKI_ENABLED=false                  # 需要 OpenAI API key 才開
      # - OPENAI_API_KEY=sk-...            # wiki 功能需要
      - TZ=Asia/Taipei
      - PUID=1000
      - PGID=1000
volumes:
  gitnexus-registry:
  gitnexus-cache:
ℹ️
All-in-one 映像的內部結構

mekayelanik/gitnexus-mcp 在容器內運行 HAProxy， 統一代理到 4747（Web UI）、39012（靜態檔案）、38011（HAProxy 內部）。 對外只暴露單一埠口（預設 8010），適合不想管理多個容器的情境。 注意這是社群非官方映像，升版需自行追蹤原始映像更新。

LadybugDB 連接池

GitNexus MCP 伺服器（LocalBackend）內建 LadybugDB 連接池， 不需要額外設定，但了解其行為有助於排查問題：

LadybugDB 連接池行為 
# LadybugDB 連接池（LocalBackend 內建，不可設定）

最大並行開啟連線數：5 個
冷啟動延遲：          ~50ms（首次開啟資料庫）
暖啟動延遲：           ~5ms（已開啟、快取中）
閒置驅逐時間：        5 分鐘無查詢自動關閉
關機時：              自動 CHECKPOINT 並清理

⚠️ 已知問題（Issue #1480）：
  gitnexus serve（HTTP 模式）在同一個 process 切換多個 repo 時，
  前一個 session 若未執行 CHECKPOINT 就關閉，lbug.wal 會留下髒頁。
  錯誤訊息：UNREACHABLE_CODE in wal_record.cpp:76

✓ 建議做法：
  • 生產環境優先使用 gitnexus mcp（stdio MCP 模式），此問題不存在
  • 若必須用 HTTP 模式，每個 repo 起一個獨立的 gitnexus serve 程序
⚠️
HTTP 模式的 WAL 殘留問題

gitnexus serve（HTTP 模式）在同一個 process 內切換多個 repo 時， 有機率留下未 CHECKPOINT 的 WAL 檔案，導致下次開啟時出現 UNREACHABLE_CODE in wal_record.cpp:76。 此問題（Issue #1480）在 MCP 模式（gitnexus mcp）不存在。 生產環境建議以 MCP 模式為主，或每個 repo 起獨立的 HTTP 程序。

Kubernetes 部署

GitNexus 官方只提供一個 Kubernetes artifact： Sigstore ClusterImagePolicy（位於 deploy/kubernetes/cluster-image-policy.yaml）。 這個 admission policy 強制叢集只接受由官方 GitHub Actions 建構並用 Cosign 簽名的映像， 拒絕任何未簽名或非官方來源的映像進入 Pod。

映像簽名驗證（Cosign）

Cosign 映像驗證 
# 驗證官方映像的 Cosign 簽名（供應鏈安全）

# 1. 驗證簽名（確認映像確實由官方 GitHub Actions 建立）
cosign verify ghcr.io/abhigyanpatwari/gitnexus:1.6.2 \
  --certificate-identity-regexp '^https://github\.com/abhigyanpatwari/GitNexus/\.github/workflows/docker\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# 2. 下載 SLSA 供應鏈來源驗證（溯源到具體 commit）
cosign download attestation ghcr.io/abhigyanpatwari/gitnexus:1.6.2 \
  --predicate-type https://slsa.dev/provenance/v1

# 受保護的映像前綴：
# ghcr.io/abhigyanpatwari/gitnexus*
# docker.io/akonlabs/gitnexus*
# akonlabs/gitnexus*

ClusterImagePolicy

deploy/kubernetes/cluster-image-policy.yaml 
# deploy/kubernetes/cluster-image-policy.yaml
# Sigstore Policy Controller — 強制只允許已簽名的官方映像進入 Pod

apiVersion: policy.sigstore.dev/v1beta1
kind: ClusterImagePolicy
metadata:
  name: gitnexus-signed-images
spec:
  images:
  - glob: 'ghcr.io/abhigyanpatwari/gitnexus*'
  - glob: 'docker.io/akonlabs/gitnexus*'
  - glob: 'akonlabs/gitnexus*'
  authorities:
  - name: gitnexus-cosign-keyless
    keyless:
      url: https://fulcio.sigstore.dev
    identities:
    - issuer: https://token.actions.githubusercontent.com
      subjectRegExp: >-
        ^https://github\.com/abhigyanpatwari/GitNexus/\.github/workflows/docker\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+
    ctlog:
      url: https://rekor.sigstore.dev
Kubernetes 部署流程 
# Kubernetes 部署流程（官方只提供 admission policy，需自行補 manifests）

# 1. 安裝 Sigstore policy-controller（一次性）

官方不提供 Helm Chart

.gitnexusrc — Repo 層級設定

在 repo 根目錄放 .gitnexusrc 可以為每個 repo 設定不同的索引行為， 不影響其他 repo：

.gitnexusrc 
// .gitnexusrc — 放在 repo 根目錄，設定此 repo 的索引行為
{
  "defaultBranch": "main",
  "skipContextFiles": true,     // 跳過 context window 用的輔助文件
  "skipSkills": true,           // 跳過 MCP Skills 產生
  "embeddings": true,           // 啟用語義向量（需要更多記憶體）
  "workerTimeout": 60           // 秒，單一 worker job 逾時
}

// 或用巢狀格式（不同指令不同設定）
{
  "analyze": {
    "defaultBranch": "develop",
    "skipSkills": true
  }
}

「內部使用」不等於「非商業」

PolyForm Noncommercial 的關鍵在於使用者是否為營利實體，而非是否對外販售。 即使是「只在公司內部給工程師用」，只要公司是營利組織，就需要取得商業授權。 違規者在收到書面通知後有 32 天補辦期，逾期授權自動終止。

商業授權請聯繫 Akonlabs：founders@akonlabs.com， 或至 GitNexus 官方 Discord 洽詢。目前商業方案分為託管 SaaS 與自托管企業版兩種， 定價按需報價（無公開價目表）。
