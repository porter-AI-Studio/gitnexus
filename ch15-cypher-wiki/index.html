第 15 章 · Part 5：進階應用與生態

Cypher 圖查詢與 Wiki 自動生成

用圖查詢語言直接對話知識圖譜，讓文件自己寫自己

前幾章介紹的 impact、context、query 等工具，是 GitNexus 為大多數場景設計的高階介面——它們已經把最常見的 查詢模式封裝好，讓 Agent 不需要了解底層圖結構就能得到有用的答案。

本章要介紹的兩個功能，面向的是想走得更深的進階玩家：

  • Cypher 圖查詢：繞過高階工具，直接用圖查詢語言讀取知識圖譜的原始資料，寫出任意形狀的自訂查詢
  • Wiki 自動生成：用 LLM 把知識圖譜轉換成人類可讀的模組文件，讓架構文件隨程式碼一起演進

一、Cypher 圖查詢

為什麼需要 Cypher？

高階工具（impact、context）的設計假設你知道「要問什麼」—— 你有一個目標符號，想知道它的上下游或影響範圍。 但有時候問題本身就是模糊的：

  • 「哪些函數橫跨了兩個不同的功能聚類？」
  • 「Authentication 模組裡，哪些符號被外部模組高置信度呼叫？」
  • 「整個 codebase 有多少孤立符號（沒有呼叫、也沒人呼叫）？」

這類開放式問題，用高階工具很難一次拿到答案。 cypher MCP 工具讓你直接對圖資料庫發送 Cypher 語言查詢， 拿回原始圖資料，就像對 SQL 資料庫下 SELECT 一樣。

底層資料庫：LadybugDB
GitNexus 使用 LadybugDB（前身為 KuzuDB）作為嵌入式圖資料庫。 LadybugDB 支援 openCypher 語法的子集，主要子句 MATCH、WHERE、RETURN、ORDER BY、 LIMIT、OPTIONAL MATCH 均可使用。

先讀 Schema，再寫查詢

下手 Cypher 前，最重要的一步是了解圖的結構。 GitNexus 透過 MCP Resource 暴露完整的 Schema： 

# 查看知識圖譜的完整 Schema
# 在使用 Cypher 前，先理解圖的結構

# 方法 1：透過 MCP Resource（推薦）
gitnexus://repo/{name}/schema

# 方法 2：Cypher 探索節點類型
MATCH (n) RETURN DISTINCT labels(n) AS nodeTypes, count(n) AS count
ORDER BY count DESC

# 方法 3：探索關係類型
MATCH ()-[r:CodeRelation]->()
RETURN DISTINCT r.type AS relType, count(r) AS count
ORDER BY count DESC

知識圖譜的主要節點與關係如下：

# GitNexus 知識圖譜 — 主要節點類型

節點類型（Node Labels）：
  Symbol        函數、類別、方法、介面等程式碼符號
  File          原始碼檔案
  Directory     目錄節點
  Community     Leiden 演算法偵測到的功能聚類（模組）
  Process       從入口點追蹤到的執行流程

Symbol 節點的常見屬性：
  name          符號名稱（如 validateUser）
  kind          類型（Function / Class / Method / Interface / ...）
  filePath      所在檔案路徑
  startLine     起始行號
  uid           唯一識別碼（格式：Kind:filePath:name）

關係類型（CodeRelation.type 的可能值）：
  CALLS         函數呼叫關係
  IMPORTS       模組匯入關係
  EXTENDS       繼承關係
  IMPLEMENTS    介面實作關係
  MEMBER_OF     隸屬於某個 Community（聚類）
  PART_OF       步驟隸屬於某個 Process（執行流）

基礎查詢範例

掌握 Schema 後，就可以開始寫查詢。以下從最簡單的情境開始：

# ── 基礎查詢範例 ──

# 1. 找出所有叫做 validateUser 的符號
MATCH (s:Symbol {name: 'validateUser'})
RETURN s.name, s.kind, s.filePath, s.startLine

# 2. 找所有 Class（限前 20 筆）
MATCH (s:Symbol {kind: 'Class'})
RETURN s.name, s.filePath
ORDER BY s.name
LIMIT 20

# 3. 找所有認證相關的 Community（聚類）
MATCH (c:Community)
WHERE c.heuristicLabel CONTAINS 'Auth' OR c.heuristicLabel CONTAINS 'Login'
RETURN c.heuristicLabel, c.id

呼叫鏈查詢

呼叫鏈是 Cypher 最有價值的使用場景——你可以沿著 CALLS 關係追蹤任意深度的上下游，並用 confidence 屬性過濾低置信度的弱關係： 

# ── 呼叫鏈查詢 ──

# 找出直接呼叫 validateUser 的所有函數
MATCH (caller:Symbol)-[r:CodeRelation {type: 'CALLS'}]->(fn:Symbol {name: 'validateUser'})
RETURN caller.name, caller.filePath, r.confidence
ORDER BY r.confidence DESC

# 找 validateUser 所有下游呼叫（往外兩層）
MATCH (fn:Symbol {name: 'validateUser'})
      -[:CodeRelation {type: 'CALLS'}*1..2]->(callee:Symbol)
RETURN DISTINCT callee.name, callee.filePath, callee.kind

# 只取高置信度的呼叫關係（>= 0.8）
MATCH (caller:Symbol)-[r:CodeRelation {type: 'CALLS'}]->(fn:Symbol {name: 'validateUser'})
WHERE r.confidence >= 0.8
RETURN caller.name, fn.name, r.confidence
ORDER BY r.confidence DESC

Cypher 的 *1..2 語法
-[:CodeRelation]*1..2-> 表示「沿此關係追蹤 1 到 2 層」。 追蹤深度越大，查詢時間越長；建議先從 1..2 開始，確認結果再加深。

聚類（Community）查詢

Community 節點是 Leiden 演算法偵測出的功能模組。 透過 MEMBER_OF 關係，你可以跨模組分析呼叫模式： 

# ── 聚類（Community）查詢 ──

# 找出 Authentication 聚類的所有成員函數，以及呼叫它們的外部符號
MATCH (c:Community {heuristicLabel: 'Authentication'})
      <-[:CodeRelation {type: 'MEMBER_OF'}]-(fn:Symbol)
MATCH (caller:Symbol)-[r:CodeRelation {type: 'CALLS'}]->(fn)
WHERE r.confidence > 0.8
RETURN caller.name, fn.name, r.confidence
ORDER BY r.confidence DESC

# 計算每個聚類的規模與平均呼叫置信度
MATCH (c:Community)<-[:CodeRelation {type: 'MEMBER_OF'}]-(s:Symbol)
OPTIONAL MATCH (caller)-[r:CodeRelation {type: 'CALLS'}]->(s)
RETURN c.heuristicLabel, count(DISTINCT s) AS memberCount,
       avg(r.confidence) AS avgConfidence
ORDER BY memberCount DESC

執行流程（Process）查詢

Process 節點代表從入口點往下追蹤到的執行路徑（如 LoginFlow、CheckoutFlow）。 用 Cypher 可以取得高階工具難以呈現的步驟細節： 

# ── 執行流程（Process）查詢 ──

# 列出所有 Process（執行流程）及其步驟數
MATCH (p:Process)
RETURN p.name, p.summary, p.stepCount
ORDER BY p.stepCount DESC
LIMIT 10

# 查某個執行流程的所有步驟，按順序排列
MATCH (s:Symbol)-[r:CodeRelation {type: 'PART_OF'}]->(p:Process {name: 'LoginFlow'})
RETURN s.name, s.filePath, r.stepIndex
ORDER BY r.stepIndex ASC

# 找哪些 Process 包含 validateUser 這個符號
MATCH (fn:Symbol {name: 'validateUser'})
      -[r:CodeRelation {type: 'PART_OF'}]->(p:Process)
RETURN p.name, p.summary, r.stepIndex

進階：跨聚類呼叫 + 孤立符號偵測

以下兩個查詢展示了 Cypher 在 codebase 健康度稽核上的應用： 找出最容易引發跨模組 Bug 的呼叫點，以及找出沒有任何連結的孤立函數： 

# ── 進階：影響鏈 + 聚類交叉分析 ──

# 找跨兩個聚類的高置信度呼叫（最容易引發跨模組 Bug 的地方）
MATCH (caller:Symbol)-[r:CodeRelation {type: 'CALLS'}]->(callee:Symbol)
WHERE r.confidence > 0.75
MATCH (caller)-[:CodeRelation {type: 'MEMBER_OF'}]->(c1:Community)
MATCH (callee)-[:CodeRelation {type: 'MEMBER_OF'}]->(c2:Community)
WHERE c1.id <> c2.id
RETURN c1.heuristicLabel AS fromModule, c2.heuristicLabel AS toModule,
       caller.name, callee.name, r.confidence
ORDER BY r.confidence DESC
LIMIT 20

# 找「孤立」符號——沒有被任何人呼叫且自己也不呼叫任何人
MATCH (s:Symbol {kind: 'Function'})
WHERE NOT (s)-[:CodeRelation {type: 'CALLS'}]->()
  AND NOT ()-[:CodeRelation {type: 'CALLS'}]->(s)
RETURN s.name, s.filePath
ORDER BY s.filePath

Cypher vs 高階工具：如何選擇？

情境 建議工具 原因
分析某個符號的影響範圍 impact 已封裝深度分組與置信度邏輯，結果直接可用
取得某個符號的上下游全貌 context 單次查詢回傳 360 度視角，比手寫 Cypher 更快
自然語言搜尋程式碼 query 混合 BM25 + 語義向量，語義搜尋需要此工具
自訂多節點關聯分析 cypher 高階工具無法表達的複雜圖模式
codebase 健康度稽核 cypher 批次統計（孤立符號、循環依賴、跨模組耦合）
探索圖 Schema 結構 MCP Resource gitnexus://repo/{name}/schema 最完整

二、Wiki 自動生成

Wiki 在解什麼問題？

軟體專案有一個普遍的矛盾：程式碼一直在演進，文件卻永遠在過期。 手寫的架構文件在兩週後可能就已經和實際程式碼脫節， 但要持續維護文件又需要大量人力。

gitnexus wiki 的思路是： 既然知識圖譜已經精確掌握了程式碼的模組結構，就讓 LLM 把圖譜翻譯成人類可讀的文件。 每次程式碼改動後重新執行，文件就能反映當前實際狀態。

工作原理

gitnexus wiki 的生成流程分三個階段：

  1. 讀取圖譜：從 LadybugDB 讀取 Community 節點、Symbol 清單、Process 路徑
  2. LLM 分組與描述：將符號分配到對應模組，對每個模組生成職責描述、 關鍵符號說明、執行流程摘要
  3. 生成 Markdown 文件：每個模組一個 .md 頁面， 加上一份整體架構概覽的 index.md

整個流程只有 LLM 呼叫需要外部網路，圖譜讀取仍在本地完成。

快速上手

# gitnexus wiki — 基本用法

# 1. 最簡單的方式（需要 OPENAI_API_KEY）
export OPENAI_API_KEY=sk-...
gitnexus wiki

# 2. 指定模型（gpt-4o 品質更好，gpt-4o-mini 速度更快）
gitnexus wiki --model gpt-4o

# 3. 使用 Anthropic / Claude
export ANTHROPIC_API_KEY=sk-ant-...
gitnexus wiki --model claude-sonnet-4-6 --base-url https://api.anthropic.com/v1

# 4. 使用 Ollama（完全本地，無 API Key 需求）
gitnexus wiki --model ollama/llama3 --base-url http://localhost:11434/v1

# 5. 強制全量重新生成（程式碼改動較多時使用）
gitnexus wiki --force

完整參數說明

# gitnexus wiki — 完整參數說明

gitnexus wiki [path]

選項：
  --model <model>       LLM 模型名稱（預設：gpt-4o-mini）
  --base-url <url>      自訂 LLM API base URL（配合 Ollama / Azure / Anthropic）
  --force               強制全量重新生成，忽略快取
  --timeout <seconds>   單次 LLM 請求逾時秒數（預設：無限制）
  --retries <n>         每次 LLM 請求的最大重試次數（預設：3）
  --lang <language>     文件輸出語言（english / chinese / spanish / japanese 等）

# 中文 Wiki（繁體中文輸出）
gitnexus wiki --lang chinese

# 大型 codebase 建議加上 timeout 與 retries 避免掛住
gitnexus wiki --model gpt-4o --timeout 120 --retries 5

Wiki 的輸出結構

生成完成後，Wiki 文件存放在 .gitnexus/wiki/。 以一個典型的電商後端專案為例： 

# Wiki 生成後的目錄結構（範例）

.gitnexus/wiki/
├── index.md              ← 整體架構概覽頁
├── authentication.md     ← Authentication 模組文件
├── payment.md            ← Payment 模組文件
├── user-management.md    ← User Management 模組文件
├── api-layer.md          ← API Layer 模組文件
└── ...                   ← 其他 Leiden 偵測出的模組

# index.md 內容結構（概覽頁）
## 專案架構概覽
- 模組清單（含每個模組的用途摘要）
- 入口點（Entry Points）
- 主要執行流程（Processes）
- 模組間依賴關係（Mermaid 圖）

# authentication.md 內容結構（模組頁）
## Authentication 模組
- 模組職責描述
- 關鍵符號（函數 / 類別）清單
- 主要執行流程（如 LoginFlow）
- 對外依賴（呼叫了哪些其他模組）
- 被誰依賴（哪些模組呼叫了這裡）

Wiki 文件的品質取決於： (1) 索引的完整度（先確認 gitnexus analyze 順利完成）； (2) 選用的模型（gpt-4o 比 gpt-4o-mini 描述更細膩）； (3) 聚類標籤的可讀性（gitnexus analyze --skills 可強化聚類語義）。

三種典型使用情境

# Wiki 的三種典型使用情境

# ──────────────────────────────────────────
# 情境 1：接手陌生 codebase
# ──────────────────────────────────────────
# 先索引，再生成 Wiki，再讓 Agent 讀 Wiki 後開始工作
gitnexus analyze
gitnexus wiki --lang chinese
# 把 .gitnexus/wiki/index.md 貼進 Claude Code 對話

# ──────────────────────────────────────────
# 情境 2：新人 Onboarding 文件
# ──────────────────────────────────────────
# 生成後提交到 docs/ 資料夾，讓新人閱讀
mkdir -p docs/architecture
cp .gitnexus/wiki/*.md docs/architecture/

# ──────────────────────────────────────────
# 情境 3：PR Review 前快速對齊架構
# ──────────────────────────────────────────
# 每次大改動後重新生成，確保文件反映最新結構
gitnexus wiki --force
git add .gitnexus/wiki/
git commit -m "docs: regenerate architecture wiki"

與 DeepWiki 的比較

GitNexus 官方 README 有一句定位聲明很清楚： 「Like DeepWiki, but deeper. DeepWiki helps you understand code. GitNexus lets you analyze it.」

面向 DeepWiki GitNexus Wiki
資料來源 直接讓 LLM 讀原始碼 LLM 讀 GitNexus 知識圖譜（預計算的關係）
準確度 取決於 LLM 的推斷品質 基於 AST 解析的確定性依賴關係
呼叫關係 描述性（可能遺漏） 完整呼叫鏈（tree-sitter 解析）
更新方式 手動觸發、需重新分析整份 codebase 可搭配 CI/CD；企業版支援自動增量更新
私有程式碼 上傳至雲端 本地索引，只有 LLM 請求發出網路

企業版：Auto-updating Code Wiki

開源版的 gitnexus wiki 需要手動觸發。 對於需要持續維護文件的團隊，GitNexus 企業版提供 Auto-updating Code Wiki， 在每次 push 後自動重新索引並更新受影響的模組文件： 

# 企業版：Auto-updating Code Wiki

# 開源版 Wiki：手動觸發
gitnexus wiki --force   ← 每次都要自己跑

# 企業版 Wiki：自動更新
# ─ 每次 git push 後自動觸發重新索引
# ─ 索引完成後自動重新生成受影響模組的 Wiki 頁面
# ─ Wiki 變更透過 PR 或通知系統推送給團隊

# 企業版的自動更新循環：
git push
  → GitNexus Auto-reindex（偵測 diff → 只更新變更模組）
  → Auto-update Wiki（只重寫受影響的 .md 頁面）
  → Notify team（透過 Webhook / Slack / Email）

Cypher 與 Wiki 的協同使用

這兩個功能其實可以組合使用。一個典型的進階工作流：

  1. 先用 gitnexus wiki 生成架構文件，快速掌握模組分布
  2. 發現某個模組（如 Payment）耦合異常，用 Cypher 查跨模組呼叫細節：
    MATCH (caller)-[r]->(callee) WHERE c1.id <> c2.id RETURN ...
  3. 把 Cypher 查詢結果貼進 Claude Code，請它分析是否需要重構
  4. 重構完成、重新索引後，用 gitnexus wiki --force 重新生成文件驗證模組邊界是否改善

讓 Agent 寫 Cypher
你不一定要自己手寫 Cypher。可以告訴 Claude Code： 「請用 cypher 工具查出所有橫跨 Auth 與 Payment 聚類的高置信度呼叫」， Agent 會先讀 Schema Resource，再生成對應的 Cypher 查詢並執行。

本章小結

cypher 和 wiki 代表 GitNexus 使用深度的兩個極端：

  • Cypher 是向下深挖——繞過封裝，直接操作圖的原始資料， 適合複雜的自訂分析和 codebase 健康度稽核
  • Wiki 是向上抽象——把圖的結構知識翻譯成人類語言， 讓文件不再是靠人力維護的靜態產物，而是可以跟著程式碼演進的活文件

掌握這兩個工具，代表你不只是在「使用」GitNexus， 而是把它當作可以深度客製化的知識圖譜後端。 下一章，我們將站到更高的視角，把 GitNexus 放進整個 AI Coding 工具生態做橫向比較， 幫你選出最適合自己工作流的組合。
