第 8 章 · Part 3：核心架構原理

LadybugDB 與混合搜尋（BM25 + Semantic + RRF）

嵌入式圖資料庫加上混合檢索，理解語義而非字串比對

第 7 章的 12 個索引階段最終把所有解析結果寫進一個圖資料庫。這個資料庫不是 PostgreSQL 也不是 Redis，而是一個嵌入式圖資料庫——不需要單獨開 server、直接以 library 形式內嵌到 GitNexus 行程中，CLI 版用 native bindings 寫到磁碟，Web 版編譯成 WASM 跑在瀏覽器。

本章解析儲存層（LadybugDB）與查詢層（混合搜尋）的技術設計。兩者密不可分：LadybugDB 同時負責圖查詢和向量索引，搜尋的三條路（BM25、語義向量、RRF 融合）都在同一個資料庫實例內完成。

從 KuzuDB 到 LadybugDB：一次關鍵遷移

GitNexus 早期版本使用 KuzuDB 作為嵌入式圖資料庫——一個由 Kùzu Inc. 開發、獲 VC 支持的開源專案。2025 年 10 月，Kùzu Inc. 將 GitHub repo 歸檔（archive）並停止維護，整個社群進入尋找繼任者的狀態。

LadybugDB 是 KuzuDB 的社群 fork，定位為「KuzuDB 唯一可行的繼任者」，由開源社群接手持續開發。GitNexus 在 CHANGELOG 的 [Unreleased] 區段記錄了這次遷移的具體內容：

  • npm 套件：kuzu → @ladybugdb/core（CLI）+ @ladybugdb/wasm-core（瀏覽器）
  • 儲存路徑：.gitnexus/kuzu → .gitnexus/lbug
  • 所有內部路徑從 kuzu 改名為 lbug
  • 加入自動清理舊 KuzuDB index 檔案的邏輯
  • 向量搜尋需明確載入 LadybugDB 的 VECTOR extension
ℹ️
從 KuzuDB 角度看 LadybugDB

LadybugDB 保留了 KuzuDB 的全部能力：OpenCypher 查詢語言、Property Graph 資料模型、ACID 事務、WASM 支援。主要變化在 v0.17.0 引入的 Icebug Format 新儲存格式，以及對 Agentic AI 應用的持續優化方向。使用者在 Cypher 查詢層面幾乎無需改動。

LadybugDB 架構

儲存格式：Icebug Format

LadybugDB v0.17.0 起採用 Icebug Format v1，副檔名為 .lbug。與舊有嵌入式資料庫（如 SQLite 把圖資料適配到表格）不同，Icebug Format 以圖結構為核心設計：

  • 欄位式（columnar）儲存：同一節點類型的屬性連續排列，批量掃描效能高
  • CSR 鄰接表（Compressed Sparse Row）：關係邊以壓縮稀疏列格式儲存，圖遍歷速度快
  • ART Index（可選）：Adaptive Radix Tree 索引，用於主鍵查找
  • 原地升級：版本升級不需要 export/reimport，直接在現有儲存上遷移
  • 零拷貝讀取：relationship table 以 Icebug 記憶體佈局讀入，省掉一次複製

查詢引擎

LadybugDB 採用向量化（vectorized）+ 因式分解（factorized）的混合執行模型：

  • 向量化執行：批量處理節點/邊資料，避免逐行呼叫開銷
  • 因式分解執行：對大型中間結果做壓縮表示，避免笛卡兒積爆炸
  • 多核心平行處理：掃描與 join 操作跨 CPU 核心分派

ACID 事務

序列化 ACID 事務（Serializable），WAL（Write-Ahead Log）保障崩潰恢復。索引完成後的知識圖譜是不可變快照，查詢時走只讀事務，不會有讀寫競爭。

GitNexus 的 LadybugDB Schema

GitNexus 圖 Schema（LadybugDB Cypher DDL） 
// GitNexus 在 LadybugDB 中建立的圖 Schema（簡化版）
CREATE NODE TABLE Symbol(
  id     STRING PRIMARY KEY,
  name   STRING,
  type   STRING,   -- "function" | "class" | "method" | "variable" | ...
  file   STRING,
  startLine INT64,
  endLine   INT64,
  signature STRING,
  embedding FLOAT[384]   -- snowflake-arctic-embed-xs 384 維向量
);

CREATE NODE TABLE File(
  path     STRING PRIMARY KEY,
  language STRING,
  hash     STRING    -- 增量索引用
);

CREATE REL TABLE Calls(FROM Symbol TO Symbol, weight FLOAT);
CREATE REL TABLE Imports(FROM File TO File);
CREATE REL TABLE Defines(FROM File TO Symbol);
CREATE REL TABLE Extends(FROM Symbol TO Symbol);
CREATE REL TABLE Implements(FROM Symbol TO Symbol);
CREATE VECTOR INDEX symbol_embedding ON Symbol(embedding);

值得注意的是 Symbol 節點包含 embedding FLOAT[384] 欄位——這是 snowflake-arctic-embed-xs 的 384 維向量，索引時一起寫入，查詢時直接從圖資料庫做向量搜尋，不需要另一套向量資料庫。

WASM 三種 Build 變體

@ladybugdb/wasm-core 三種 build 
// @ladybugdb/wasm-core 的三種 build 變體

// 1. Default（無多執行緒）— 最廣泛相容
//    適用：瀏覽器 + Node.js，不需 COOP/COEP headers
import { Database } from '@ladybugdb/wasm-core';

// 2. Multi-threaded（需 cross-origin isolation）
//    適用：高效能瀏覽器場景（需 COOP: same-origin + COEP: require-corp）
import { Database } from '@ladybugdb/wasm-core/multi-threaded';

// 3. Node.js build（CommonJS，不可用於 Browser）
//    適用：CI / 後端腳本
import { Database } from '@ladybugdb/wasm-core/nodejs';

// 瀏覽器記憶體模式（GitNexus Web 預設）
const db = new Database(':memory:');

// 持久化到 IndexedDB（透過 IDBFS）
const db = new Database('/idbfs/gitnexus.lbug');

GitNexus Web 版預設使用 Default 變體（無多執行緒），因為它不需要 Cross-Origin Isolation headers（COOP: same-origin + COEP: require-corp），相容性最廣。如果部署環境支援 COOP/COEP，可切換 Multi-threaded 變體獲得更高解析速度。

Cypher 查詢介面

LadybugDB 使用 OpenCypher 作為查詢語言，這也是 GitNexus cypher MCP tool 的底層。幾個典型的知識圖譜查詢：

Cypher 查詢：呼叫者、影響範圍、Cluster 成員 
-- 查找 validatePayment 的所有呼叫者（一跳）
MATCH (caller:Symbol)-[:Calls]->(target:Symbol {name: "validatePayment"})
RETURN caller.name, caller.file, caller.startLine
ORDER BY caller.file;

-- 查找影響半徑：深度 3 的下游符號
MATCH (src:Symbol {name: "processPayment"})-[:Calls*1..3]->(downstream)
RETURN DISTINCT downstream.name, downstream.file;

-- 找到某個 cluster 的所有成員
MATCH (s:Symbol)
WHERE s.clusterId = "cluster_auth"
RETURN s.name, s.type
ORDER BY s.type, s.name;

-- 混合搜尋後的圖擴展（先找 symbol，再拿鄰居）
MATCH (s:Symbol {id: $symbolId})-[r]-(neighbor)
RETURN s, r, neighbor
LIMIT 50;

相較於 SQL，Cypher 的模式匹配語法在圖遍歷上更自然——MATCH (a)-[:Calls*1..3]->(b) 直接表達「最多三跳的呼叫鏈」，不需要遞迴 JOIN。

BM25：詞彙搜尋的精準層

BM25 是資訊檢索的經典算法，命中精確識別符特別有效——輸入函式名稱就能精準定位。

BM25 公式與程式碼識別符 Tokenization 
# BM25 公式
# score(d, q) = Σ IDF(t) · [ tf(t,d) · (k1+1) ] / [ tf(t,d) + k1·(1 - b + b·|d|/avgdl) ]

# 參數說明
k1 = 1.5    # 詞頻飽和度（程式碼搜尋常用 1.5–2.0，比一般文字 1.2 略高）
b  = 0.75   # 文件長度正規化（0 = 完全不正規化，1 = 完全正規化）

# 程式碼識別符的特殊 Tokenization
# camelCase 拆分：getUserName → ["get", "user", "name"]
# snake_case 拆分：calculate_total_price → ["calculate", "total", "price"]
# 數字分隔：oauth2Token → ["oauth", "2", "token"]
# 大寫縮寫保留：parseHTTPRequest → ["parse", "HTTP", "request"]

# BM25 vs 純詞頻計數
# 純詞頻：函式名出現 10 次的貢獻是出現 1 次的 10 倍 → 不合理
# BM25：透過 k1 對詞頻做 S 型飽和，避免長檔案無條件勝出

程式碼搜尋的關鍵挑戰是 tokenization：getUserName 作為單一詞彙的 IDF 會非常高（只出現在少數地方），但使用者可能輸入 get user 或 user name。GitNexus 把識別符拆成子詞：

  • getUserName → get、user、name（camelCase 拆分）
  • validate_payment_amount → validate、payment、amount（snake_case 拆分）
  • parseHTTPRequest → parse、HTTP、request（大寫縮寫保留）

BM25 的搜尋對象包含：函式/方法名稱、簽名、所屬模組路徑。同一檔案在多個節點類型中命中時，BM25 分數相加。

Semantic Search：語義向量的深度層

BM25 的弱點是「詞彙不重疊就命中失敗」。使用者問「JWT token 產生」時，函式叫 signAccessToken 的 BM25 分數很低——但語義上完全相關。這就是向量搜尋的用武之地。

snowflake-arctic-embed-xs + transformers.js 
// GitNexus 使用 Snowflake/snowflake-arctic-embed-xs
// 22M 參數、384 維輸出、MTEB NDCG@10 = 50.15

import { pipeline } from '@xenova/transformers';

// 載入 embedding pipeline（首次使用時下載模型快取到本地）
const extractor = await pipeline(
  'feature-extraction',
  'Snowflake/snowflake-arctic-embed-xs'
);

// 索引時：符號名稱 + 函式簽名 → 嵌入向量（儲存到 LadybugDB）
async function embedSymbol(symbol) {
  const text = `${symbol.name} ${symbol.signature}`;
  const output = await extractor(text, { pooling: 'cls', normalize: true });
  return Array.from(output.data);  // Float32Array → 普通陣列
}

// 查詢時：加上 "query:" prefix（arctic-embed 的 bi-encoder 設計需要）
async function embedQuery(queryText) {
  const output = await extractor(`query: ${queryText}`, {
    pooling: 'cls',
    normalize: true
  });
  return Array.from(output.data);
}

// LadybugDB 向量搜尋（需載入 VECTOR extension）

為什麼選 snowflake-arctic-embed-xs？

規格 數值 意義
參數量 22M（基於 all-MiniLM-L6-v2） 體積小，WASM 可接受
嵌入維度 384 精度與儲存的平衡
MTEB NDCG@10 50.15 接近 100M 參數模型精度
架構 Bi-encoder（retrieval 優化） 查詢與文件獨立編碼，高效
執行環境 ONNX Runtime Web（WASM / WebGPU） 瀏覽器零依賴

這是通用文字嵌入模型（非程式碼專用），但針對 retrieval 任務優化，在各 MTEB/BEIR benchmark 的小型模型中屬 SOTA 水準。查詢時需加上 query: prefix——這是 arctic-embed bi-encoder 的設計需求，讓模型區分「查詢句」與「文件句」的表示空間。

💡
WebGPU 加速

transformers.js 預設用 WASM 模式執行，在支援 WebGPU 的瀏覽器（Chrome/Edge 原生，全球約 70% 覆蓋）可啟用 GPU 加速，速度比 WASM 快約 64 倍。GitNexus Web 版在偵測到 WebGPU 支援時自動切換，不支援時 fallback 到 WASM——使用者無需任何配置。

RRF：讓兩條路的排名相加

BM25 的分數範圍是 (0, +∞)，向量的 cosine similarity 範圍是 (0, 1)——這兩個分數直接相加毫無意義。如果要加權平均，還需要精細調參，且對不同 codebase 的泛化性很差。

RRF（Reciprocal Rank Fusion） 解決了這個問題：它完全忽略原始分數，只看排名位置，把兩份排名清單融合成一份。

RRF 公式、計算範例與 k=60 的設計意義 
# RRF（Reciprocal Rank Fusion）公式
# Cormack, Clarke & Buettcher 2009 SIGIR

# RRF_score(doc) = Σᵣ 1 / (k + rankᵣ(doc))

# GitNexus 的雙路融合（k = 60）：
# RRF(doc) = 1/(60 + rank_bm25(doc)) + 1/(60 + rank_semantic(doc))

# 範例計算：
# doc A → BM25 rank=1, semantic rank=5
#   RRF_A = 1/(60+1) + 1/(60+5) = 0.01639 + 0.01538 = 0.03177

# doc B → BM25 rank=10, semantic rank=1
#   RRF_B = 1/(60+10) + 1/(60+1) = 0.01429 + 0.01639 = 0.03068

# doc C → 只出現在 BM25 rank=3，semantic 未命中
#   RRF_C = 1/(60+3) + 0 = 0.01587

# 結果排名：A > B > C（doc A 兩路都有好名次，獲得最高融合分）

# k=60 的設計意義：
# k 是阻尼常數，防止前幾名的分數差距過大
# k=60 時，rank=1 的貢獻是 1/61 ≈ 0.0164
#          rank=60 的貢獻是 1/120 ≈ 0.0083（仍有 50% 的貢獻）
# → 即使只在一個路徑中排名靠前，也不會被完全忽視

RRF 的核心優勢

  • 無需分數正規化：不同量綱的分數（BM25 vs cosine）完全不影響 RRF
  • 對兩條路各自排名名次穩健：即使某文件在一條路中排名很差，另一條路的好排名仍能挽回
  • k=60 阻尼設計：防止前幾名分數差距過大，讓排名靠後但在兩條路都有出現的文件仍有機會進入最終結果
  • 生產環境無需調參：k=60 在大量實驗中被驗證為通用最佳值，小型語料庫可降至 k=20，超大型可升至 k=100

實測數據（電商搜尋資料集）：

  • NDCG 評分：混合 RRF 0.750 vs BM25 單獨 0.698 vs 純向量 0.695（提升 7.4%）

⚠️
LadybugDB 向量搜尋需明確載入 Extension

從 KuzuDB 遷移到 LadybugDB 後，向量搜尋功能需要在使用前明確載入 VECTOR extension：CALL db.loadExtension('vector')。GitNexus 在初始化資料庫連線時自動處理這個步驟，但如果你直接用 cypher MCP tool 執行向量查詢，需要確認 extension 已載入。

索引時間分析

混合搜尋的代價在索引時，不在查詢時：

  • BM25 索引：FTS 索引在圖寫入時同步建立，無額外時間
  • 語義向量：每個 Symbol 需要一次 embedding 推論（--embeddings flag 啟用）
  • 首次索引（含 embedding）：10 萬行 repo 約 3–8 分鐘（視 CPU/GPU）
  • 增量索引（含 embedding）：只處理變更符號，通常 30 秒以內
  • 查詢時：BM25 + 向量搜尋 + RRF 融合在 LadybugDB 內完成，通常 <50ms

小結：為什麼搜尋要走三條路

任何單一搜尋方式在 codebase 查詢上都有死角：BM25 對語義盲，純向量對精確識別符弱，圖遍歷缺乏入口發現能力。 GitNexus 把三者疊在一起——BM25 快速定位精確識別符，語義向量捕捉意圖與同義，RRF 無縫融合兩份排名而不需要調參——讓 AI agent 無論用精確名稱還是描述性語言查詢，都能拿到正確的起始節點，再用圖遍歷展開完整的依賴上下文。

儲存層（LadybugDB）之所以是關鍵選擇，正是因為它同時支援圖查詢與向量索引，讓搜尋結果到圖擴展的整個路徑都在同一個嵌入式資料庫內完成，CLI 跑磁碟、瀏覽器跑 WASM，兩套環境共用同一份邏輯。
