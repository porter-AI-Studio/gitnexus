第 11 章 · Part 4：MCP 整合與 Agent 實戰

16 個 MCP 工具詳解

impact、context、query、detect_changes、rename、cypher——每個工具一次講透

工具總覽

GitNexus 透過 MCP（Model Context Protocol）暴露 16 個工具。分為兩類：

類型 數量 用途
Per-repo 工具 11 個 針對單一 repo 的查詢、分析、搜尋
Multi-repo 群組工具 5 個 跨多個 repo / 微服務的契約提取與比對

Per-repo 核心工具

impact — 爆炸半徑分析

GitNexus 最核心的工具。在修改任何函式、類別或模組前，先用 impact 確認影響範圍：

impact 工具：爆炸半徑分析 
# impact 工具：爆炸半徑（Blast Radius）分析
# 修改某個符號前，先看影響範圍

用法（在 Claude Code 中對話觸發）：
  "use gitnexus impact to analyze validatePayment"
  "如果修改 UserService.login，會影響哪些程式碼？"

返回結果格式：
  d=1（WILL BREAK）  ← 直接呼叫方，必須同步更新
    - checkout.ts:89    processCheckout()
    - auth.ts:142       authenticateUser()

  d=2（LIKELY AFFECTED）  ← 間接依賴，建議測試
    - payment.ts:203    handlePayment()
    - webhook.ts:67     processWebhook()

  d=3（MAY NEED TESTING）  ← 傳遞鏈路，核心路徑測試
    - metrics.ts:45     trackConversion()

Confidence: 0.87 (high)

impact 返回三層影響：

  • d=1（WILL BREAK）：直接呼叫方，修改後必須同步更新，否則一定壞
  • d=2（LIKELY AFFECTED）：間接依賴，建議回歸測試
  • d=3（MAY NEED TESTING）：傳遞鏈路，核心路徑上建議測試

每個 impact 結果附帶 Confidence 置信度評分（0-1），反映圖譜在這個節點的完整性。

context — 符號 360 度視角

取得某個符號的完整上下游關係——誰呼叫它、它呼叫誰、它屬於哪些執行流程：

context 工具：符號完整上下文 
# context 工具：符號 360 度視角
# 一次拿到某個符號的所有上下游關係

用法：
  "use gitnexus context on validatePayment"
  "给我看 UserAuthService 的所有調用關係"

返回：
  Symbol: validatePayment (function)
  File: src/payments/validator.ts:42
  Cluster: payments

  Callers (5):          ← 誰呼叫了我
    checkout.ts:89        processCheckout
    subscription.ts:34    renewSubscription
    ...

  Callees (3):          ← 我呼叫了誰
    formatCurrency (utils/format.ts:12)
    fetchExchangeRate (api/rates.ts:78)
    ...

  Processes (2):        ← 我屬於哪些執行流程
    checkoutFlow (入口: api/checkout → 47 步驟)
    subscriptionRenewal (入口: cron/renewal → 23 步驟)

context 最適合用在「我需要理解這個函式在整個系統中的角色」這類問題，或者在接手陌生模組時快速定向。

query — 混合搜尋

用自然語言搜尋 codebase，結合 BM25 關鍵字匹配和語義向量搜尋，RRF 融合排名：

query 工具：混合搜尋 
# query 工具：混合搜尋（BM25 + 語義向量 + RRF）
# 支援自然語言語義搜尋（需要 --embeddings）

用法：
  "use gitnexus query to find authentication logic"
  "搜尋處理支付失敗的程式碼"
  "find rate limiting middleware"

返回：排序後的相關符號清單
  1. validateToken (auth/jwt.ts:23) — score: 0.92
     呼叫方: 12個  呼叫: 3個  Cluster: auth

  2. AuthMiddleware (middleware/auth.ts:8) — score: 0.87
     呼叫方: 8個  呼叫: 5個  Cluster: auth
  ...

# BM25（關鍵字）+ 語義向量（HuggingFace transformers.js）
# RRF（Reciprocal Rank Fusion）融合排名
💡
query 對比 grep 的優勢

傳統 grep 只能搜尋字串，用「handle user authentication」搜不到叫 validateJWT 或 checkCredentials 的函式。query 的語義向量理解意思，把「authentication」和「validateToken」、「AuthMiddleware」連結起來——這就是語義搜尋。

detect_changes — Git Diff 影響映射

在 commit 前用 detect_changes 確認這次修改的實際影響——不只是「改了哪些行」，而是「影響了哪些執行流程」：

detect_changes 工具：變更影響分析 
# detect_changes 工具：Git diff 影響映射
# 把「改了哪幾行」轉換成「影響哪些執行流程」

用法：
  "use gitnexus detect_changes"
  "分析這次 commit 的實際影響"
  （在 commit 前執行最有用）

工作原理：
  1. 讀取 git diff（當前 uncommitted changes 或指定 commit）
  2. 找到被修改行對應的符號
  3. 映射到包含這些符號的執行流程（Processes）
  4. 返回受影響的流程清單及風險評估

返回示例：
  Changed: validator.ts:42-67 (validatePayment)

  Affected Processes:
    ⚠️  checkoutFlow     (HIGH risk — 核心支付路徑)
    ⚡  subscriptionFlow (MEDIUM risk)
    ✓   testPayment      (LOW risk — 僅測試路徑)

這個工具特別適合搭配 Claude Code 的 PostToolUse Hook：在 git commit 後自動觸發，確認索引是否過期，並提示 Claude 分析本次提交的影響範圍。

rename — 安全跨檔案重命名

重構時需要重命名符號，rename 用圖搜尋 + 文字搜尋雙重保險找出所有引用位置：

rename 工具：安全跨檔案重命名 
# rename 工具：安全跨檔案重命名
# 返回所有需要同步更新的位置

用法：
  "use gitnexus rename to find all references to validatePayment"
  "找出所有 UserService 的引用位置，我要重命名"

工作原理（雙重保險）：
  1. 圖搜尋：從 LadybugDB 的邊關係找到所有 references
  2. 文字搜尋：全文搜尋所有字串出現位置
  最終取聯集，確保不遺漏

返回：
  References to validatePayment (23 locations):
    src/checkout.ts:89
    src/payments/processor.ts:34
    tests/payment.test.ts:12
    docs/api.md:45        ← 連文件裡的引用也找到
    ...

注意：rename 工具只「返回位置清單」，實際重命名操作
由 Claude Code 的 Edit 工具執行——職責分離。

cypher — 原始圖查詢

進階用戶可以直接執行 Cypher 查詢，探索 LadybugDB 中的完整圖結構：

cypher 工具：原始 Cypher 圖查詢 
# cypher 工具：原始 Cypher 圖查詢
# 直接查 LadybugDB，給進階用戶

用法示例（Cypher 查詢語法）：
  # 找所有沒有被任何地方呼叫的函式（孤立函式）
  MATCH (n:Symbol {type: 'function'})
  WHERE NOT (()-[:CALLS]->(n))
  RETURN n.name, n.file

  # 找兩個符號之間的最短路徑
  MATCH path = shortestPath(
    (a:Symbol {name: 'checkout'})-[:CALLS*]-(b:Symbol {name: 'sendEmail'})
  )
  RETURN path

  # 找循環依賴
  MATCH (a:Symbol)-[:IMPORTS]->(b:Symbol)-[:IMPORTS]->(a)
  RETURN a.name, b.name
ℹ️
Cypher 查詢語言

Cypher 是 Neo4j 開創的圖查詢語言，現已成為 openCypher 開放標準。LadybugDB 支援 Cypher 查詢，語法與 Neo4j 相同。常用的模式匹配：MATCH (n)-[:CALLS]->(m)（n 呼叫 m）、shortestPath()（最短路徑）、MATCH path = (n)-[*1..5]->(m)（最多 5 跳的路徑）。

list_repos — 倉庫清單

列出全局 registry 中所有已索引的 repo，包括索引時間、符號數量、狀態：

用法："use gitnexus list_repos"
返回：
  ● my-app (/Users/porter/projects/my-app)
    Symbols: 81,400  Relations: 191,438  Last indexed: 2h ago  Status: current
  ● api-service (/Users/porter/projects/api-service)
    Symbols: 23,100  Status: stale (8 files changed since last index)

Per-repo 其他工具

工具 功能 典型使用時機
list_clusters 列出 Leiden 偵測的所有功能集群及成員 理解專案整體模組劃分
list_processes 列出所有追蹤到的執行流程（從入口到終點） 找到某個業務功能對應的程式碼路徑
status 查看當前 repo 的索引狀態（是否 stale） 確認索引是否需要更新
wiki 基於知識圖譜生成專案 Wiki（會呼叫 LLM API） 自動維護程式碼文件

Multi-repo 群組工具（5 個）

群組工具適合微服務架構或 monorepo — 把多個互相依賴的 repo 組成群組，分析跨服務的契約與依賴：

多倉庫群組工具 
# 多倉庫群組工具（5 個）— 跨服務追蹤

# 1. group_list — 列出所有群組
gitnexus group list

# 2. group_create + group_add — 建立群組並加入 repo
gitnexus group create my-services
gitnexus group add my-services backend/api api-service
gitnexus group add my-services backend/worker worker-service

# 3. group_sync — 提取契約並做跨 repo 比對
# MCP 工具呼叫："use gitnexus group_sync on my-services"
# 提取各 repo 的 API 契約（HTTP routes、函式介面）
# 跨 repo 比對：找到 caller 在 service-A 呼叫
# 而 callee 定義在 service-B 的跨服務呼叫鏈

# 4. group_contracts — 查看契約清單
# 5. group_query — 在群組內跨 repo 搜尋執行流程
# 6. group_status — 檢查群組內所有 repo 的索引是否過期
工具 功能
group_list 列出已配置的所有倉庫群組
group_sync 提取各 repo 的 API 契約（HTTP routes、函式介面），跨 repo 比對呼叫方與被呼叫方
group_contracts 查看 group_sync 提取出的完整契約清單與跨連結
group_query 在群組內跨 repo 搜尋執行流程
group_status 檢查群組內所有 repo 的索引是否過期（stale 偵測）
ℹ️
群組工具的使用前提

群組工具需要每個 repo 分別完成 gitnexus analyze，並用 gitnexus group add 加入群組。group_sync 才能在本地的多個索引間做跨 repo 契約比對，整個過程仍然是零伺服器、本地執行。Enterprise 版本的多 repo 功能提供統一的跨倉庫圖譜（而不是多個獨立索引的拼接）。
