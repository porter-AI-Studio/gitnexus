第 13 章 · Part 4：MCP 整合與 Agent 實戰

實戰場景：PR Review、Bug 定位、安全重構

從修改前到提交後，每個開發階段該用哪個工具

四大核心場景

場景一：PR Review — 爆炸半徑評估

傳統 PR Review 依賴 reviewer 對程式碼庫的記憶，容易遺漏隱式依賴。GitNexus 把「這個 PR 改動了哪些執行流程」量化成可執行的清單：

PR Review 爆炸半徑分析 
# 場景 1：PR Review 爆炸半徑分析
# 在 Claude Code 中，拿到一個 PR 的 diff 後：

# Step 1：分析變更影響（貼入 PR diff 或直接執行）
gitnexus analyze  # 確保索引最新
# 然後在 Claude Code 中：
"use gitnexus detect_changes to analyze the impact of this PR"
"用 gitnexus impact 分析修改 validatePayment 的影響範圍"

# Step 2：Claude 呼叫 detect_changes 後輸出：
# Changed: payments/validator.ts:42-67 (validatePayment)
# Changed: payments/validator.ts:89-102 (formatCurrency)
#
# Affected Processes:
#   ⚠️ checkoutFlow     (HIGH risk — 核心支付路徑，300個執行步驟)
#   ⚡ subscriptionFlow (MEDIUM risk — 訂閱更新路徑)
#   ✓  testPaymentMock  (LOW risk — 僅在測試環境)
#
# 建議：在合併前對 checkoutFlow 和 subscriptionFlow 執行回歸測試
💡
影響等級說明

⚠️ HIGH risk = 核心執行路徑，建議 block merge 直到測試通過；⚡ MEDIUM risk = 建議加測試後 merge；✓ LOW risk = 可安全 merge，僅影響測試或邊緣路徑。這個分類不是 GitNexus 用 LLM 推斷的，而是基於圖中的路徑深度和邊的類型確定性計算的。

場景二：Bug 定位 — 從報告到根因

收到一個模糊的 bug 報告時，傳統做法是一層一層 grep 往下找，GitNexus 把這個過程壓縮成 3 次工具呼叫：

Bug 定位：query → context → impact 
# 場景 2：Bug 定位與根因分析
# 已知報告：「用戶無法完成支付，錯誤出現在結帳流程」

# Step 1：語義搜尋找到相關程式碼
"use gitnexus query to find payment error handling code"
# 返回：PaymentErrorHandler, validatePayment, processCheckout...

# Step 2：查看完整上下文
"use gitnexus context on processCheckout"
# 返回：
#   Callers: 2個（checkoutController, retryQueue）
#   Callees: validatePayment, chargeCard, sendReceipt
#   Processes: checkoutFlow, mobileCheckoutFlow

# Step 3：影響分析
"use gitnexus impact on chargeCard"
# 找到 chargeCard 在兩個流程中的角色，
# 進而定位到近期改動了 chargeCard 的 d=1 依賴

# 關鍵對比（無 GitNexus）：
# 平均需要 14 次 grep + 6 次 Read = 20 個工具呼叫
# 使用 GitNexus：3 次 MCP 呼叫定位根因
步驟 工具 目的 工具呼叫次數
找入口 query 用語義搜尋定位相關程式碼 1 次
理解角色 context 看完整的呼叫鏈與流程歸屬 1-2 次
找根因 impact 追蹤哪個上游符號的改動觸發了問題 1 次
傳統 grep 法 grep + Read — 平均 14-20 次

場景三：安全重構 — 跨檔案重命名

重構時最怕的就是「改了這裡，不知道還有哪裡要改」。rename 工具的雙重保險（圖搜尋 + 全文搜尋）確保不遺漏任何引用，包括文件中的引用：

安全重構：rename + impact 雙重確認 
# 場景 3：安全重構 — 重命名跨檔案符號
# 目標：把 validatePayment 重命名為 validateTransaction

# Step 1：找出所有引用位置（跨 23 個檔案）
"use gitnexus rename to find all references to validatePayment"
# 返回：
#   References to validatePayment (23 locations):
#     src/payments/processor.ts:89
#     src/checkout/checkout.ts:142
#     src/subscription/renewal.ts:67
#     tests/payment.test.ts:12, 34, 56
#     docs/api.md:45              ← 文件裡的引用也找到！
#     ...

# Step 2：影響分析確認改動代價
"use gitnexus impact on validatePayment"
# 確認 d=1 呼叫方清單，與 rename 結果比對

# Step 3：Claude Code 執行批次重命名
# Claude 拿到完整清單後，用 Edit 工具逐一修改，
# 不會遺漏任何引用位置
ℹ️
rename 工具不執行實際重命名

rename 只返回「所有需要修改的位置清單」，實際的檔案修改由 Claude Code 的 Edit 工具執行。這個職責分離是刻意的設計：GitNexus 負責「知道哪裡要改」，Claude Code 負責「實際去改」，各自做最擅長的事。

場景四：新人 Onboarding — 30 分鐘理解遺留系統

接手一個陌生的大型 repo 時，list_clusters + list_processes 提供一個從高層到細節的探索路徑：

新人 Onboarding：clusters → processes → context 
# 場景 4：新人 Onboarding — 快速理解遺留系統
# 新進成員第一天，面對 8 萬行程式碼的 repo

# Step 1：理解整體架構分區
"use gitnexus list_clusters to show the project's functional areas"
# 輸出 47 個 Cluster：
#   auth（認證，12個符號）
#   payments（支付，31個符號）
#   notification（通知，18個符號）
#   ...

# Step 2：找到核心業務流程
"use gitnexus list_processes to show main execution flows"
# 輸出 300 個 Processes，最重要的：
#   checkoutFlow（入口: POST /api/checkout，47 步驟）
#   userRegistration（入口: POST /auth/register，23 步驟）
#   subscriptionRenewal（入口: CRON daily，31 步驟）

# Step 3：深入理解核心模組
"use gitnexus context on PaymentService"
# 拿到 PaymentService 與整個系統的完整關係圖

# 效果：
# 沒有 GitNexus：新人平均需要 3-5 天才能基本摸清架構
# 有 GitNexus：30 分鐘內理解核心模組依賴關係

各開發階段工具選用準則

階段 情境 推薦工具 預期收益
修改前 不確定改這個函式會影響哪些地方 impact 消除「盲改」風險
不了解要修改的模組 context 快速掌握上下游關係
除錯時 找到 bug 的相關程式碼 query 語義搜尋找到完全不同命名的相關程式碼
追查根因（哪個改動觸發） context + detect_changes 從呼叫鏈定位責任節點
重構時 重命名符號 rename 不遺漏任何引用，包括文件
確認重構代價 impact 量化 d=1/2/3 的影響範圍
提交前 確認這次改動的實際影響 detect_changes git diff → 受影響執行流程的清單
架構探索 第一次接觸專案 list_clusters + list_processes 30 分鐘建立架構全貌
進階圖探索 cypher 自訂查詢，找循環依賴、孤立函式

實測效果對比

根據社群回報的實測資料，在影響分析類型的任務上：

指標 不使用 GitNexus 使用 GitNexus
找到 bug 根因的平均工具呼叫次數 14-20 次（grep/Read 組合） 3-5 次（MCP 工具）
PR Review 遺漏隱式依賴的概率 高（依賴 reviewer 記憶） 低（圖譜覆蓋所有關係）
跨檔案重命名的完整性 容易遺漏文件、非直接引用 圖搜尋 + 全文搜尋雙重保險
新人理解核心架構所需時間 3-5 天 30-60 分鐘（視專案規模）
ℹ️
即使小模型也能勝任複雜分析

GitNexus 官方文件特別指出：「Even smaller models get full architectural clarity」。原因是 MCP 工具把複雜的圖分析工作提前做完，Claude 只需要「讀懂工具返回的結構化結果」，而不是「自己從幾十個 grep 結果中推論出架構圖」。後者對模型能力的要求高得多。
