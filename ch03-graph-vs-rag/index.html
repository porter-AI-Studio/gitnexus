第 3 章 · Part 1：認識 GitNexus

知識圖譜 vs Vector RAG vs Graph RAG

預計算結構 vs 運行時探索：三種技術路線的本質差異，以及為什麼一次查詢就能返回完整上下文

問題的本質：程式碼理解 ≠ 文字相似度

讓 AI 理解程式碼，本質上是在解一道「context window 與 retrieval」的拉扯問題：context window 永遠塞不下整份 repo，retrieval 又要在對的時間拿到對的那塊。

過去主流做法分兩條路：

  • 語義搜尋派（Vector RAG）：把程式碼切成 chunk，用 embedding 模型轉向量，查詢時算 cosine similarity 找最相關片段
  • 讓 AI 自己探索派（grep + read）：Claude Code、Cursor 等工具主動 grep 關鍵字、讀檔案、決定看哪裡

這兩條路都有同一個致命傷：回傳的是程式碼片段，不是程式碼關係。它們能告訴你「程式碼在哪裡」，但找不到「程式碼之間怎麼連」。

三條技術路線的對比

技術路線 核心機制 能做到 做不到 對 AI 的代價
Vector RAG Embedding 向量 + cosine similarity 用自然語言找語義相似的程式碼片段 跨檔案呼叫鏈；詞彙不重疊的隱性依賴；同名符號的命名空間區分 回傳片段仍需 AI 自行讀檔拼湊關係
Graph RAG（運行時） 查詢時讓 LLM 走圖探索（hop by hop） 比向量更精準的結構查詢，能走多跳 依賴 LLM「恰好探索到」關鍵路徑，多跳推理容易漏；每次對話重算 多次查詢鏈，長上下文中答案漂移
預計算關係智慧（GitNexus） 索引時完成聚類/呼叫鏈/影響範圍計算，查詢時走圖 traversal 單次工具呼叫返回完整呼叫鏈、依賴、影響範圍；結果確定性高 描述性/風格類問題（vector 更適合）；動態語言的部分呼叫推斷有誤差 一次工具呼叫，零 LLM Token 消耗

GitNexus 官方對此有一句精準的描述：

"Traditional approaches give the LLM raw graph edges and hope it explores enough. GitNexus precomputes structure at index time."

傳統做法把原始圖邊給 LLM，祈禱它自己探索夠多。GitNexus 在索引時就把結構算好。

Vector RAG 的典型失敗模式

向量搜尋在程式碼場景有三個系統性的弱點：

  1. 詞彙不重疊的呼叫關係：payment/checkout.ts 裡的 processOrder() 透過三層中間呼叫最終呼叫了 auth/login.ts 的 validateSession()，但因為兩個檔案幾乎沒有共同關鍵字，向量搜尋永遠找不到這條連線
  2. 同名符號的命名空間混淆：不同模組都有 create()、update() 這種通用名稱，向量搜尋會把所有無關的同名函式一起拉回來
  3. Chunk 邊界切斷關係：一個函式的定義跨越了 chunk 邊界，呼叫關係被截斷，LLM 只看到殘缺的片段
向量 RAG 的典型失敗場景 
# 向量 RAG 的典型失敗場景

問題：「UserService.login 被哪些模組呼叫？」

向量搜尋找到的（詞彙相似片段）：
  → auth/login.ts      ← 函式定義本身
  → tests/auth.test.ts ← 測試檔（詞彙相似）
  → docs/auth.md       ← 文件（語義相似）

向量搜尋「漏掉」的（無詞彙重疊）：
  → api/middleware.ts  → verifyRequest() → login()
  → payment/hooks.ts   → onCheckout() → login()
  → admin/session.ts   → refreshAdmin() → login()

# 這 3 個真正的呼叫者都找不到，因為它們
# 不含「UserService」或「login」關鍵字

圖查詢如何解決這個問題

GitNexus 在索引階段就用 Tree-sitter 解析每個函式的呼叫關係，把它們存成圖的邊（Edge）。查詢時走 graph traversal——不管呼叫者和被呼叫者的詞彙有多不同，只要圖裡有邊，就能找到。

# 預先計算好呼叫圖，查詢走 graph traversal

impact("UserService.login") →

GitNexus 的 Node/Edge 圖模型

知識圖譜的基礎是清楚定義節點（Node）與邊（Edge）的類型。GitNexus 的圖模型：

Node/Edge 模型 
# GitNexus 的 Node/Edge 圖模型

節點類型（Node Types）：
  Function  — 函式、方法
  Class     — 類別
  Module    — 模組、檔案
  Variable  — 模組層級變數
  Type      — 型別、介面（TypeScript/Go/Rust）

邊類型（Edge Types）：
  CALLS       → A 呼叫 B
  IMPORTS     → A 匯入 B
  EXTENDS     → A 繼承 B
  IMPLEMENTS  → A 實作介面 B
  REFERENCES  → A 參考型別 B
  CONTAINS    → 模組包含符號

混合搜尋：圖結構 + 語義向量

GitNexus 並不是純圖查詢，它用 BM25 + Semantic Embeddings + RRF（Reciprocal Rank Fusion） 三路融合：

  • BM25：傳統關鍵字排名，命中精準但對語義差異敏感
  • Semantic Embedding（HuggingFace transformers.js）：語義向量相似度，補 BM25 的語義缺口
  • RRF：用倒序排名加權合併兩路結果，比任一單路都準
三路混合搜尋範例 
# BM25 + Semantic + RRF 混合搜尋

使用者問：「JWT 在哪裡生成？」

BM25（關鍵字排名）找到：
  → auth/jwt.ts::sign()        score: 0.92
  → auth/jwt.ts::verify()      score: 0.88
  → config/auth.ts::JWT_SECRET score: 0.71

Semantic（語義向量）找到：
  → auth/token.ts::createToken()   score: 0.87  ← 沒有 "JWT" 字面
  → auth/session.ts::issueSession() score: 0.74  ← 語義相關
  → auth/jwt.ts::sign()             score: 0.91

RRF 融合後最終排名：
  1. auth/jwt.ts::sign()         (兩路都高分)
  2. auth/token.ts::createToken() (語義命中補了 BM25 的缺口)
  3. auth/jwt.ts::verify()
💡
什麼時候 Vector RAG 反而更好？

GitNexus 本身也整合了向量搜尋——對於描述性問題（「這個 repo 的整體風格是什麼？」「這段程式碼在做什麼業務邏輯？」）向量搜尋反而比圖查詢直觀。GitNexus 的混合策略就是讓兩者各司其職：圖查詢負責結構關係，向量搜尋負責語義理解。

預計算的代價與邊界

預計算帶來精準度，但也有它的邊界條件：

限制 說明 GitNexus 的處理方式
動態語言的呼叫推斷 Python、Ruby 的動態 dispatch 無法 100% 靜態解析 置信度（confidence）評分標記不確定的邊，impact 工具回傳時標示
索引需要時間 大型 monorepo 首次索引需要數分鐘 增量索引（只更新變更檔案）、detect_changes 追蹤 Git diff
程式碼變更後需要重新索引 改了程式碼，圖譜可能過期（stale） PostToolUse Hooks 在 git commit 後自動提示重新索引
某些架構模式的識別精度 複雜的工廠模式、反射、macro 生成的呼叫 持續改進解析器；Scope-Resolution Pipeline（RFC #909）提升準確度
ℹ️
小結：選哪條路？

如果你的 AI Coding 需求主要是局部生成（寫一個函式、解釋一段程式碼），Vector RAG 或讓 AI 自己 grep 就夠用。但如果你需要跨檔案重構、影響範圍分析、依賴追蹤、PR 審查這些結構性任務，GitNexus 的預計算知識圖譜才能提供可靠的上下文。不是取代關係，而是適合不同任務層次。
